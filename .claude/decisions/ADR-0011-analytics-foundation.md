# ADR-0011 — Analytics Foundation: Separate Event Table, Genuine Fire-and-Forget, No New RBAC Gate

## Context

Sprint 6.5 adds an Analytics Foundation: the data and query layer Sprint 6.6's Production Dashboard will visualize, tracking Content/Image/Video Generation, Brand Kit usage, Review workflow, Publishing, Provider usage, Generation duration, Review duration, Approval metrics, and Project activity. The explicit instruction was to reuse existing events wherever possible, avoid duplicate logging, and never let analytics failures interrupt normal workflows.

Research confirmed almost every tracked metric is already answerable by querying existing tables (`AssetReview`, `AssetReviewEvent`, `PublishingRecord`, and the `provider`/`model`/`generationTimeMs`/`brandKitId` columns already on `GeneratedContent`/`GeneratedImage`/`VideoAsset`) — with exactly one gap: a first-time generation writes zero event/log row anywhere. `ContentService`/`ImageService`/`VideoAssetService.generate()` never touch `AssetReviewEvent`; that table is only entered later, once an asset is touched by the Asset Library/QA workflow. Three decisions in this sprint are worth recording.

## Decision 1: A new, separate `AnalyticsEvent` table, not a write into `AssetReviewEvent`

The one genuine gap — no event log for first-time generation — needs exactly one new write. The two options were: write a new `GENERATED` value into the existing `AssetReviewEvent` table, or introduce a small, separate `AnalyticsEvent` table with the same append-only, polymorphic `(assetType, sourceId)` shape.

`AssetReviewEvent` was explicitly scoped by ADR-0009 to *review-relevant activity* — every existing write into it happens inside `AssetService`, which is the one component that bridges plain generation and the review/versioning/publishing layer. `ContentService`, `ImageService`, and `VideoAssetService` today have zero coupling to `AssetService`, `AssetReviewEventRepository`, or the review/versioning layer at all. Writing generation events directly into `AssetReviewEvent` from these three services would create a second, independent write-path into a table whose purpose was deliberately scoped, and would blur a boundary this codebase has otherwise kept clean across three prior sprints.

`AnalyticsEvent` is a new table, but not new *storage of existing data* — it captures only the one fact nothing else records (that a generation happened, with its provider/model/duration/brand-kit-usage snapshot), keyed identically to `AssetReviewEvent` so both tables can be merged into one activity feed trivially. `provider`, `model`, `generationTimeMs`, and `brandKitId` are real columns, not JSON, specifically so `groupBy`-style aggregation (provider usage, generation duration, brand kit usage) works directly — mirroring why `GeneratedImage`/`VideoAsset` already have real `provider`/`model` columns instead of a JSON blob.

**Alternative considered and rejected**: add a `GENERATED` value to `ReviewEventType` and write it from the generation services directly into `AssetReviewEvent`. Rejected — it would require `ContentService`/`ImageService`/`VideoAssetService` to depend on `AssetReviewEventRepository`, a layer they've never touched, and would mean two independent code paths (three generation services, plus `AssetService`'s own seven methods) writing into a single table whose whole design assumed one writer (`AssetService`) with a stable, review-scoped meaning.

## Decision 2: The analytics write is genuinely unawaited (fire-and-forget), not just awaited-and-swallowed

This codebase already has one pattern for "a secondary write that shouldn't fail the primary operation": `ImageService.delete()`/`markFailed()` and `VideoAssetService.delete()` all `await` the secondary write inside a `try`/`catch`, logging on failure but never re-throwing. Every one of those, though, protects a real invariant — e.g. a user must always be able to remove an image from their history even if disk cleanup fails, but the deletion still needs to actually attempt to finish before the response goes out.

The analytics write protects no such invariant. There is no correctness requirement that an `AnalyticsEvent` row exist before the generation response is returned — it is purely observational. The more literal, and more correct, implementation of "fire-and-forget" here is to not await the write at all: call `analyticsEventRepository.create(...)`, attach a `.catch()` that logs the failure, and return immediately. This is a genuine first inside a request path in this codebase — the only prior unawaited-`.then().catch()` pattern (`logComfyUIHealthCheck()`/`logHuggingFaceHealthCheck()`) runs once at server boot, not per-request — but the underlying mechanism (an unhandled-rejection-safe unawaited promise) is the same, just extended into request scope for the first time.

**Alternative considered and rejected**: match the existing awaited-but-swallowed pattern exactly, for consistency. Rejected — that pattern exists specifically because those writes protect a real invariant; applying it here would add real (if usually small) latency to every generation request for a write nothing depends on completing before responding.

## Decision 3: No new RBAC gate on the analytics endpoints

`"analytics"` and `"dashboard"` permission names already exist in the seed data and are already granted to the `Owner` role, but are otherwise unused anywhere in the codebase. Despite that, the new `/api/v1/analytics/...` endpoints stay `authenticate`-only, consistent with every other Content Studio route and with ADR-0009/0010's established reasoning: this repo's global RBAC governs page-level feature access, not per-resource ownership, and analytics-about-your-own-projects is exactly the same ownership category as everything else in Content Studio — a project's owner can already see everything about that project; seeing a rollup of the same data introduces no new access boundary to gate.

**Alternative considered and rejected**: gate the new endpoints with `requirePermission("analytics")`, since the permission already exists and is unused. Rejected — it would make analytics the first Content Studio feature ever access-gated below the page level, a real precedent shift, for a feature that doesn't actually need a narrower access boundary than everything else already has. If a genuinely cross-user, admin-facing analytics view is ever built, that would be the natural place to finally put the existing `"analytics"`/`"dashboard"` permissions to use — not this sprint's per-owner rollups.

## Consequences

- `AnalyticsEventType` is a new, minimal enum (`GENERATED` only today) with room to grow additively, the same posture `ReviewEventType` already has.
- `ContentService`, `ImageService`, and `VideoAssetService` each gained one new constructor parameter (`analyticsEventRepository`, default-instantiated) and one new fire-and-forget call at the end of a successful generation. No existing method signature, error type, or control-flow path changed — verified directly in tests by making the faked `analyticsEventRepository.create()` reject and confirming `generate()` still resolves normally.
- `AssetReviewEventRepository`, `AssetReviewRepository`, and `PublishingRecordRepository` each gained one new, additive `findManyByProject(projectId)` method — none of the three previously supported a project-wide query, only per-asset or per-source-id-pairs lookups.
- Review/publishing performance metrics are computed in-memory from `AssetReviewEvent` rows (pairing the first `NEEDS_REVIEW`→`APPROVED` transition, and the first `PUBLISH_STARTED`→`PUBLISHED` transition, per asset), the same aggregation-in-the-service-layer posture `AssetService.list()` already established (ADR-0008) rather than a database-level rollup query.
- Publishing performance is computed per `(assetType, sourceId)`, not per `(assetType, sourceId, platform)` — `AssetReviewEvent` doesn't carry `platform` as a first-class column (only inside `metadata`), so an asset published to two platforms in overlapping windows would have its `PUBLISH_STARTED`/`PUBLISHED` pairs computed across both indiscriminately. Accepted as a "Foundation"-level approximation, not corrected this sprint — flagged explicitly rather than silently accepted.
- `AnalyticsEvent.brandKitId` is a plain string, not a foreign key — deliberately, so a later `BrandKit` deletion never has to touch historical analytics rows (same reasoning `GeneratedImage.brandKitId`'s `SetNull` relation already establishes, just without a relation at all here since this is a historical snapshot).
- Sprint 6.5 ships backend-only, matching the precedent Sprint 4.1 already set (a complete backend pipeline shipped before any frontend existed for it) — Sprint 6.6 builds the dashboard UI (via the already-installed, previously-unused `recharts` dependency) on top of these endpoints.
