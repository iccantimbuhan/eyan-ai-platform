## Restaurant Onboarding Workflow (Sprint 1.4)

Populating a new restaurant's real master data is a one-time, manually-run seed script — not a UI workflow, not an OCR/AI importer (that's an explicitly deferred future sprint, built only after Inventory). The process, as run for Burger's Ink and Topo Gigio:

1. Gather real source material (photographed menus, photographed/forwarded supplier order sheets, any manually-typed ingredient lists) — real data only, never invented.
2. Transcribe menu items **verbatim**, including their printed ingredient descriptions where present. Items with only a name and price (no description) get a `MenuItem` row but deliberately **no `Recipe`** — "enough information exists" (this sprint's own bar) means a real ingredient list, not just a name.
3. Normalize ingredient names across sources (fix obvious misspellings, merge case/spelling variants — e.g. "Mozarella"/"Mozzarella" → one row) and strip purchase-pack-size suffixes ("25KG", "1KG") out of the name — pack size is a purchasing concern, not the ingredient's identity (ADR-0037).
4. Build Suppliers from the real order sheet, and link each Ingredient to every Supplier the source data actually shows it under — **do not assume one ingredient has one supplier**; the same real order sheet can (and did, for Burger's Ink's "Frying Oil") show one ingredient sourced from multiple suppliers.
5. **Do not seed `Unit` rows.** Units are restaurant-specific and entered manually through the UI by restaurant staff who know their own purchasing/recipe units. Since `RecipeIngredient.unitId` is a required foreign key, this means **no `RecipeIngredient` rows can exist until Units are entered** — that's expected, not a bug. A `Recipe` container can still be created (its `notes` field documents that lines are pending).
6. Never invent a quantity, weight, cost, or food-cost percentage that isn't in the source data. If it's not written down, it's not in the seed.
7. Write the script as idempotent find-by-`(restaurantId, name)`-then-create (same pattern as `seed-restaurant-tenancy.ts`) — safe to re-run, and this is what structurally prevents duplicate menu items/ingredients/suppliers/recipes, rather than a separate manual check.
8. Run once via `npx tsx prisma/seed-restaurant-product-onboarding.ts` against the target database — **not** wired into `bootstrap.ts`'s automatic deploy chain (real customer data isn't platform-required scaffolding, same "manual only" posture as `seed-demo-content.ts`).

Source data for Burger's Ink/Topo Gigio: `/home/eyancantimbuhan/Data Photos/` (photographed menus + the real "ORDER LIST BURGERS INK PAOLA" supplier sheet — outside the repository, not committed, since it's real customer material) plus a manually-provided, already-normalized Topo Gigio ingredient list.

## Tenant hierarchy

`Organization → Restaurant → Branch`. `Organization` is the one reusable tenant/membership/billing root (a future non-restaurant module would hang off the same primitive). `Restaurant` (a brand, e.g. Burger's Ink) and `Branch` (a physical location) are this module's own domain vocabulary beneath it — not platform-level.

Business data splits by ownership level, per the approved domain model (not uniformly Branch-scoped): **Menu** (`MenuCategory`, `MenuItem`) and **product knowledge** (`Ingredient`, `IngredientCategory`, `Supplier`, `Unit`, `Recipe`, `RecipeIngredient` — Sprint 1.3, ADR-0037) are **Restaurant-scoped**, since these are brand-level facts true at every Branch identically; **Inventory** (`InventoryItem`, `StockMovement` — Sprint 2A, ADR-0038) and **Sales** (`DailySalesRecord` and its four line-entry tables — Sprint 2C, ADR-0039) are **Branch-scoped** — each consumes the product catalog per-Branch (how much is on hand / sold *here*) but never owns or redefines it. Sales' three reference lists (`SalesChannel`/`SalesPaymentMethod`/`SalesCategory`) are Restaurant-scoped configurable vocabulary, same posture as `Unit`. Purchases/Expenses/Daily Closing/Reports (Sprint 2B/3+) will also be Branch-scoped. Whichever level a table belongs to, every repository query against it must filter by that id — no exceptions, see Rules below.

## Inventory Foundation (Sprint 2A)

`InventoryItem` (one row per `(branchId, ingredientId)`, unique-constrained) tracks `currentQuantity`/`minimumQuantity` for an Ingredient at a Branch. `StockMovement` is a separate, append-only audit ledger (`OPENING_STOCK`/`ADJUSTMENT`/`WASTE`/`STOCK_COUNT`) — `currentQuantity` is a running balance updated only inside the same transaction as the movement that justifies it (`stock-movement.repository.ts`'s `record()`), never independently, so it structurally can't drift from the ledger or be silently mutated without history. Stock status (`IN_STOCK`/`LOW_STOCK`/`OUT_OF_STOCK`) is computed server-side from the two quantities on every read, never stored.

Creating an `InventoryItem` *is* recording opening stock — there's no separate "create then set opening stock" step, and opening stock can only be set once, at creation. Adjustments accept a signed delta; waste accepts a positive quantity the service negates; stock counts accept the absolute physical count and the service computes the delta against the current system quantity. Negative `currentQuantity` is allowed (not clamped) — see ADR-0038 Decision 4.

Reads (list/detail/movement history) are open to any `BranchMember` role. Writes (opening stock, minimum-threshold update, adjustment, waste, stock count) require `requireTenantRole('OWNER', 'MANAGER', 'SUPERVISOR', 'INVENTORY_STAFF')` — `CASHIER`/`KITCHEN`/`ACCOUNTANT`/legacy `STAFF` can view but not mutate. First real usage of the `INVENTORY_STAFF` role. Access itself is gated by a new `createBranchScopedAccessGuard` factory (`requireInventoryItemAccess`) — the Branch-first counterpart to `createRestaurantScopedAccessGuard`, walking the same three-tier chain `requireBranchAccess` already implements. See ADR-0038.

Explicitly out of scope for Sprint 2A (deferred to Sprint 2B/3): automatic stock deduction from `RecipeIngredient` quantities on a sale, purchase-driven stock increases, food costing, actual-vs-theoretical variance.

## Sales Foundation (Sprint 2C)

`DailySalesRecord` (one row per `(branchId, businessDate)`, unique-constrained) is one business day's manually-entered sales record for one Branch — sourced from a printed POS Z/X report and/or Wolt/Bolt/MyPOS/Cash channel totals, never from a POS integration. It carries the record's own authoritative `totalSales` plus separate POS report metadata (`posReportType`/`posReportNumber`/`posReportedTotal`) and `discountsTotal`/`vouchersAmount`/`vouchersCount`/`notes`. Four child line-entry tables (`SalesChannelEntry`, `SalesPaymentMethodEntry`, `SalesCategoryEntry`, `SalesItemEntry`) hold that day's breakdown; each is created/deleted individually, mirroring `RecipeIngredient`'s own header-plus-repeatable-lines shape rather than a single batch payload.

Three Restaurant-scoped configurable master lists back the entry tables — `SalesChannel`, `SalesPaymentMethod`, `SalesCategory` — same posture as `Unit`: not hardcoded, a manager adds their own inline from the entry form. **Channel and payment method are always kept separate** (Wolt is a channel; Electronic is a payment method; Cash can legitimately be both, as two separate rows in two separate tables) and their totals are never reconciled against each other or against `totalSales`/`posReportedTotal` — every figure is preserved exactly as entered, even if they don't sum to match. `SalesCategory` is deliberately independent of `MenuCategory` (a POS category printout isn't guaranteed to mean the same thing). Itemized sales (`SalesItemEntry`) snapshot `itemName`/`categoryName` as plain strings at write time; `menuItemId` is an optional `onDelete: SetNull` cross-reference only, never read for display — a later Menu rename/delete can never corrupt historical sales.

Daily retrieval (`GET /branches/:branchId/sales/daily?date=`) resolves the one record for a branch+date directly. Weekly aggregation (`GET /branches/:branchId/sales/weekly?startDate=&endDate=`) is computed fresh on every read in plain `Prisma.Decimal` arithmetic over the range's raw records — no stored weekly total, no BI engine, matching `StockStatus`'s computed-not-stored precedent.

Reads (daily/weekly/single-record) are open to any `BranchMember` role. Writes (record create/update, all four line-entry types, and the three master-list creates) require `requireTenantRole('OWNER', 'MANAGER', 'SUPERVISOR', 'ACCOUNTANT')` — swaps Inventory's `INVENTORY_STAFF` for `ACCOUNTANT`, since Sales is financial/bookkeeping data. Access itself is gated by `requireSalesRecordAccess`, built from the same `createBranchScopedAccessGuard` factory Inventory introduced — no new authorization pattern. See ADR-0039.

Explicitly out of scope for Sprint 2C (deferred to later sprints, per its own spec): POS API/webhook integration, WhatsApp/OCR/AI ingestion, recipe-based automatic inventory deduction, purchasing, food costing, daily closing workflow, and any AI-generated commentary or profitability calculation.

## Sales Reporting & Analytics Foundation (Sprint 2D)

Turns Sprint 2C's raw `DailySalesRecord`/entry rows into management reporting — zero schema changes, every figure computed fresh on read in `SalesAggregationService` (extends the same class Sprint 2C introduced) and in `daily-sales-record.mapper.ts` for the single-day case. Nothing here is stored.

**Coverage** (`WeeklySalesSummaryDto.coverage`): `daysInRange`/`daysRecorded`/`missingDays`/`missingDates[]`/`averageSalesPerRecordedDay`, computed by enumerating every calendar date in the requested range (via `truncateToUtcDate`) and diffing against the dates that actually have a `DailySalesRecord`. A day with no record is listed in `missingDates` and excluded from `daysRecorded` — it is never treated as €0 sales, anywhere in the calculation or the UI (`SalesCoverageCard`).

**Percentages** (`ChannelTotalDto.percentOfChannelEntriesTotal` and the equivalent for payment methods/categories): each is a share of that breakdown's *own* recorded total (e.g. a channel's amount ÷ Σ all channel entries in range), never a share of `totalSales`/`posReportedTotal` — those remain independent figures per ADR-0039 Decision 2, so a "% of total" framing would misleadingly imply reconciliation. `null` when the breakdown's own total is zero (no division by zero).

**Channel performance** (`ChannelTotalDto.activeDays`/`averageAmountPerActiveDay`): `activeDays` is the count of `SalesChannelEntry` rows for that channel across the range (max one per day, so this is exactly "days this channel had a recorded entry"). The UI (`ChannelPerformanceSection`) labels the top channel by amount and by average/day with neutral badges ("Highest recorded sales" / "Highest average sales/day") — never "best channel," since gross sales alone doesn't establish profitability across platforms with different commissions/pricing.

**Reconciliation** (`SalesReconciliationDto`, on both the weekly summary and — new for Sprint 2D — the single-day response via `DailySalesRecordResponseDto.reconciliation`): surfaces `totalSales` vs. `posReportedTotal` vs. `channelEntriesTotal` and their variances side by side. A non-zero variance is never auto-corrected and never labeled an error — the UI (`ReconciliationCard`) shows a neutral "Requires review" badge and an explicit note that independent figures aren't automatically reconciled (ADR-0039 Decision 2/3, unchanged — Sprint 2D only surfaces what was already true).

**Comparison** (`GET /branches/:branchId/sales/comparison?currentStartDate=&currentEndDate=&previousStartDate=&previousEndDate=`, `SalesAggregationService.getComparison`): both periods are supplied explicitly by the caller — the backend never infers "the previous period." Internally calls `getWeeklySummary()` twice and diffs `totalSales`/channel/category/top-item breakdowns, unioned by key so an entry present in only one period still gets a row (its other side is a real "0", not a data gap). `changePercent` is `null` — not `Infinity`/`NaN` — whenever the previous period's value is zero; the frontend (`SalesComparisonSection`) renders that as "No comparison data."

**Trend chart** (`SalesTrendChart`): plots only recorded days (`dailySales[]`) via the existing `recharts` dependency (already used by Finance/CRM dashboards) — a missing day has no bar at all rather than a zero-height one, so it can never be visually confused with a real €0 day.

Explicitly out of scope for Sprint 2D, same as 2C: POS/delivery-platform API integration, WhatsApp, OCR, AI interpretation, inventory deduction, recipe consumption, purchasing, daily closing.

## Sprint 2B Prep — UX Improvements

Not Sprint 2B itself (no inventory/recipe consumption here) — a focused set of fixes and small extensions making the existing Menu/Ingredients/Recipes/Sales workflows usable enough for a manager to enter real data while Sprint 2B waits. Two genuinely new pieces of data (both additive, one migration); everything else is UI/UX.

**Category filters** (Menu Items, Ingredients): a client-side TanStack facet on the existing `category` column, reusing `DataTableFacetedFilter` exactly the way Status already does — no server round-trip, no duplicated category data. `DataTableFacetedFilter`'s trigger button now carries `aria-label="Filter by {title}"`, since its visible text ("Category"/"Status") otherwise collides with `DataTableColumnHeader`'s own same-named sort-menu button in the accessible tree.

**"Add Recipe" fix**: traced end-to-end (frontend dialog → hook → API → route → validator → controller → service → repository → Prisma) and live-tested the real HTTP path — the create flow itself was already correct. The actual, reproducible defect: for a restaurant where every menu item already has a recipe (confirmed live — Topo Gigio Pizzeria, 32/32), the button was silently `disabled` with zero explanation, indistinguishable from broken. Fixed by adding `lib/recipe-availability.ts`'s `computeRecipeAvailability()` (pure, unit-tested) and surfacing its `reason` string next to the button — never by hiding or further disabling it.

**Clickable recipe menu-item name**: the Menu Item cell in `recipe-columns.tsx` is now a button opening the *same* `RecipeIngredientsDialog` instance the row's "Manage Ingredients" action already used — the dialog's open state was lifted from `RecipeActions` up to `RecipeTable` (keyed by recipe id, not a captured object, so it stays live across query invalidation) specifically so there is exactly one dialog implementation shared by both trigger points, not two.

**Recipe notes**: `Recipe.notes` was never a status field, but Sprint 1.4's onboarding script had accidentally used it as one — every seeded recipe carried a hardcoded sentence about pending manual Unit entry. Root-caused, fixed at the source (the seed script no longer writes anything into `notes`), and the 68 real dev-DB rows carrying that exact placeholder text were cleaned to `null` via one exact-match `UPDATE` (verified: 68/68 rows affected, row count unchanged). The dialog's Notes field now explains its real purpose ("optional prep or operational instructions... not a status field") with real examples as its placeholder; the table shows "No notes" rather than a bare dash.

**Daily Sales — Category → Menu Item**: `ItemEntrySection` gained a Category `<Select>` that filters the existing Menu Item `<Select>` client-side (no new endpoint — `useMenuItems`'s existing optional `menuCategoryId` server param stays unused here deliberately, since the full item list is already small and loaded). Selecting a menu item still only *populates* `itemName`/`categoryName`/`amount` as a convenience; the submitted `SalesItemEntry` is unchanged — still a plain snapshot, still optional `menuItemId`, still supports pure manual entry for POS items with no menu match (refunds, specials, etc.).

**Channel-specific menu pricing** (ADR-0040): new `SalesChannelMenuItem` table — an optional `(SalesChannel, MenuItem)` price/availability override, `@@unique` on the pair, `restaurantId` denormalized. `MenuItem.price` is never overwritten; a missing row means "use the base price on this channel." Managed via a new "Channel Prices" action on the Menu Items page (`ChannelPricesDialog`) and read wholesale per restaurant (`GET /restaurants/:restaurantId/sales-channel-menu-items`, mirrors the other Sales reference lists); mutated one channel at a time (`PUT`/`DELETE /menu-items/:itemId/channel-prices/:salesChannelId`, scoped by the existing `requireMenuItemAccess()` guard, same write-role list as Sprint 2C's Sales writes). `ItemEntrySection` gained an optional Sales Channel selector purely to look up this override and suggest a channel-aware default `Amount` when a menu item is picked — the override is never written onto `SalesItemEntry`.

**Manual POS %Qty/%Sales**: `SalesItemEntry` gained two optional `Decimal(5,2)` columns, `posQuantityPercent`/`posSalesPercent` — the POS X/Z report's own printed %QT/%SALE columns, transcribed manually. Explicitly **not** Sprint 2D's computed analytics percentages (those are still derived, never stored); the UI labels these fields "POS % Qty"/"POS % Sales" to keep the distinction visible. Validated 0–100 server-side; both optional, since not every entry comes from a POS report.

Explicitly not built this sprint (same non-goals as every Sales/Inventory sprint before it): Sprint 2B's own recipe-based stock consumption, POS/Wolt/Bolt API integration, WhatsApp, OCR, AI extraction/interpretation, forecasting.

## POS Source / Sales Channel Flexibility (ADR-0041)

Real restaurants run different POS/channel topologies — one POS covering every channel, multiple POS terminals each covering a different subset of channels, or a single POS/single-channel setup — and the relationship can change over time. `PosSource` is a fourth Restaurant-scoped master list (same shape as `SalesChannel`/`SalesPaymentMethod`/`SalesCategory`), but it is **never** linked to `SalesChannel` at the master-list level — no `posSourceId` column on `SalesChannel` itself, since that would hardcode a permanent POS-to-channel mapping. Instead, `SalesChannelEntry` gained an optional `posSourceId` (plus `transactionCount`, mirroring `SalesPaymentMethodEntry`) — each day's channel-amount *line* optionally records which POS terminal reported it. A single-POS restaurant (every real restaurant on the platform today) never touches the field; a multi-terminal day tags each line with the POS that reported it. As of ADR-0042 (below), the same channel can carry a different `posSourceId` on the same day too, not only across different days.

`DailySalesRecord`'s existing single POS-report header fields (`posReportType`/`posReportNumber`/`posReportedTotal`) are untouched — confirmed with the user rather than adding a `SalesPosReport` child table this sprint. Per-POS reporting granularity is answered entirely by two new computed aggregation fields in `SalesAggregationService.getWeeklySummary`: `posSourceTotals[]` (Σ amount/Σ transactionCount per POS source, plus an explicit never-dropped "unassigned" bucket for entries with no `posSourceId`) and `channelsByPosSource[]` (one row per POS source, each with its own channel breakdown — answers "sales by POS + channel combination"). The frontend's `PosSourcePerformanceSection` renders only when at least one entry has actually been tagged with a real POS source, so restaurants that never use the feature see nothing new. See ADR-0041.

## Payment Method POS Source Flexibility, and a Shared Uniqueness Fix (ADR-0042)

Extends the exact same `posSourceId` pattern to `SalesPaymentMethodEntry` — the same payment method (e.g. "Wolt," which can legitimately appear both as a Sales Channel and, separately, as a POS-reported Payment Method — never confused with each other) can be reported under multiple POS terminals on the same business day (POS 1: Cash/Card/Wolt; POS 2: Wolt/Bolt). An architecture assessment (presented and approved before implementation) found that `SalesChannelEntry`'s own unique constraint — unchanged since Sprint 2C, not touched by ADR-0041 — actually limited a channel to **one entry per day, total**, contradicting ADR-0041's own text; both `SalesChannelEntry` and `SalesPaymentMethodEntry`'s unique constraints were widened in the same migration from `(record, channel/method)` to `(record, channel/method, posSourceId)`. Because Postgres treats `NULL` as distinct from every other `NULL` in a unique index, the service-layer duplicate pre-check moved from `findUnique` on the compound key to a `findFirst`-based plain equality lookup (`posSourceId: null` renders as `IS NULL`, correctly catching a duplicate no-POS entry too). New `paymentMethodPosSourceTotals[]`/`paymentMethodsByPosSource[]` aggregation fields mirror the channel ones exactly but are kept **strictly separate** — a POS's channel total and its payment-method total are independent facts, never summed into one combined POS figure (same reasoning as ADR-0039's channel-vs-payment-method separation). `PaymentMethodEntrySection` gained the identical POS Source select `ChannelEntrySection` already had; `PosSourcePerformanceSection` gained a second, independently-gated block for payment methods. See ADR-0042.

## Product Foundation (Sprint 1.3)

`Ingredient` optionally belongs to one `IngredientCategory` (soft grouping — deleting a category un-categorizes its ingredients via `SetNull`, unlike Menu's ownership cascade) and links to many `Supplier`s via the `IngredientSupplier` join table (many-to-many, no pricing yet — confirmed necessary by Burger's Ink's real order sheet, where "oil" is sourced from two different suppliers). `Unit` is a Restaurant-scoped, configurable unit-of-measure master list (g/kg/piece/...), not hardcoded.

`Recipe` belongs to exactly one `MenuItem` (`menuItemId` unique — enforced at the service layer with a pre-check, `MenuItemAlreadyHasRecipeError`, not just the DB constraint) and owns a list of `RecipeIngredient` lines (`ingredientId`, `unitId`, `quantity`, unique per `(recipeId, ingredientId)`). This is pure product-knowledge data — no stock deduction, no Inventory linkage; Inventory (Sprint 2+) will read this catalog, never own it.

An Ingredient's linked Suppliers are written via `supplierIds: string[]` on the same create/update call — the full set is replaced on write, mirroring `roles.service.ts`'s `updateRolePermissions` pattern, not a separate attach/detach endpoint.

All six new tenant-access guards (`requireUnitAccess`/`requireIngredientCategoryAccess`/`requireSupplierAccess`/`requireIngredientAccess`/`requireRecipeAccess`/`requireRecipeIngredientAccess`) share one `createRestaurantScopedAccessGuard` factory in `tenant.middleware.ts` — all six resources denormalize `restaurantId` directly onto the row (same posture as `MenuItem`), so the guard shape is identical across all of them; factored out to avoid six copy-pasted implementations.

## Two authorization axes — never conflate them (ADR-0036)

- **Platform RBAC** ("what modules can this user access at all") — the existing global `Role`/`Permission` system, completely unchanged in mechanism. Commercial customer users hold exactly one platform Role, `Restaurant Customer`, granted only the `restaurant` Permission — this alone hides AI Core/CRM/Finance/Content Studio/Administration from them via the same `useCan()`/`useModuleEnabled()` nav gating every other module already uses.
- **Tenant Role** ("what can this user do inside a Restaurant") — `TenantRole`, now seven named roles: `OWNER`, `MANAGER`, `SUPERVISOR`, `CASHIER`, `KITCHEN`, `INVENTORY_STAFF`, `ACCOUNTANT` (plus legacy `STAFF`, kept for Postgres compatibility, never assigned going forward). Enforced by `requireTenantRole(...roles)` in `tenant.middleware.ts`.

## Membership

Three independent junction tables, all `(userId, scopeId, role: TenantRole, assignedAt)`, composite-keyed, no separate id: `OrganizationMember` (access to every Restaurant/Branch under the Organization), `RestaurantMember` (scopes to one Restaurant, never its siblings), `BranchMember` (scopes to one Branch — added Sprint 1.2, amending ADR-0025's earlier YAGNI call now that a real customer needs it). A user can legitimately hold multiple grants at once (e.g. `RestaurantMember` on two of three restaurants).

**Effective role resolution is most-specific-wins**: a direct `BranchMember` role is used if present, otherwise the `RestaurantMember` role for the resolved restaurant, otherwise the `OrganizationMember` role for the resolved organization. This is what `requireTenantRole` computes (via `req.tenantContext`, populated by whichever tenant-access guard ran first in the chain — no extra query) and what `organization.mapper.ts`'s `myRole` fields mirror for frontend display.

Bootstrap seeding (`seed-restaurant-tenancy.ts`) still grants `OrganizationMember(OWNER)` to every user who already holds the platform's global `Owner` role — unchanged since Sprint 0. Onboarding real staff is Sprint 1.2's Staff Management feature.

## Staff Management (Sprint 1.2)

`StaffMembershipService` — one upsert method (`upsertMembership`) serves Invite/Assign Role/Assign Restaurant/Assign Branch identically, differing only in which scope is targeted; inviting a brand-new email creates the `User` (+ grants `Restaurant Customer`, additive, never touches an existing broader Role) and requires a name+password (no email-invite channel exists — ADR-0034 deferred Email); inviting an existing email just adds/updates a grant. "Disable Staff" hard-deletes every membership row under that Organization — deliberately not a reuse of `User.isActive`, which is global and would incorrectly lock a multi-tenant user out of unrelated Organizations. Takes effect on the user's next request (`authenticate()` reloads memberships fresh every time, no stale-JWT window).

Two route surfaces, same service underneath: `/organizations/:organizationId/staff` (`requireOrganizationAccess`) and `/restaurants/:restaurantId/staff` (`requireRestaurantAccess`, restaurant-scoped-only Managers aren't locked out; can only grant `RESTAURANT`/`BRANCH` scope, never `ORGANIZATION`). Both gated by `requireTenantRole('OWNER', 'MANAGER')`. Frontend currently only calls the Organization-scoped path (`/app/restaurant/staff`) — the Restaurant-scoped one exists on the backend for a future enhancement, not wired to a page yet.

## Rules

- **Every Restaurant repository query must filter by `branchId`/`restaurantId` — no exceptions.** This is the opposite of Finance/CRM's precedent (`.context/finance.md`, `.context/crm.md`): those are deliberately global shared workspaces with no per-row filtering.
- `requirePermission("restaurant")` gates *whether* a user can use the module at all; `requireRestaurantAccess`/`requireBranchAccess`/`requireOrganizationAccess`/`requireMenuCategoryAccess`/`requireMenuItemAccess` gate *which* Organization/Restaurant/Branch/Menu Category/Menu Item they can act on; `requireTenantRole` (composed after one of those) gates *what they can do* once there. All three layers, always — never skip one.
- A client-supplied foreign key into a sibling tenant-scoped table (e.g. `MenuItem.menuCategoryId`, `StaffMembership.restaurantId`/`branchId`) is never trusted without re-verifying it belongs to the already-authorized parent — see `MenuCategoryMismatchError`/`StaffScopeMismatchError`. A route's tenant-access guard only proves the id *in the URL* is authorized; it says nothing about IDs inside the request body.
- `requireTenantRole` must always be composed *after* a tenant-access guard on the same route — it reads `req.tenantContext`, which only that guard populates, and fails closed (denies) if it's missing.
- The Module Registry (`OrganizationModule`, gated via `useModuleEnabled()`) and the `Restaurant Customer` platform Role both control nav/route *visibility* only. Neither is the real enforcement — `requirePermission`/`requireRestaurantAccess`/`requireBranchAccess`/`requireTenantRole` are.
- **Known gap, partially resolved in Sprint 2A and Sprint 2C**: Branch-scoped-only staff (Cashier/Kitchen/Supervisor/Inventory Staff, no Restaurant/Organization membership) still cannot reach Menu Category/Item routes or the Sprint 1.3 Ingredient/Recipe/Supplier/Unit routes — those are unchanged, still gated by `requireRestaurantAccess`/`createRestaurantScopedAccessGuard`, neither of which considers `BranchMember`. Inventory (Sprint 2A) and Sales (Sprint 2C) are the domains that close this for themselves: both are genuinely Branch-scoped, both use `createBranchScopedAccessGuard` (via `requireInventoryItemAccess`/`requireSalesRecordAccess`, which do consider `BranchMember`, at tier 1), and both pair it with a read/write `requireTenantRole` split. See ADR-0036/0037's Consequences for the still-open part, ADR-0038/ADR-0039 for the resolved parts.
- **Real customer data now exists in the dev database** (Sprint 1.4, both restaurants) — treat `eyan_ai_platform_dev`'s Ingredient/Supplier/MenuItem/Recipe rows as real, not disposable test fixtures. Sprint 2 work (and any future ad-hoc dev-DB testing) should create its own throwaway rows rather than mutating or deleting this onboarded data; the `seedRestaurantProductOnboarding` script is idempotent and safe to re-run if it's ever accidentally cleared.
- Do not reuse `Finance.Expense` for restaurant expenses when that module ships (Sprint 3) — same word, unrelated domain and tenancy model. Do not route Slack (Sprint 7) through `eyan-automation-hub` — see ADR-0034.
- Master-data list endpoints (Restaurant/Branch/Menu Category/Menu Item/Staff) are deliberately unpaginated — realistic row counts per restaurant don't warrant Finance Expense's pagination machinery yet.

ADR-0040 fills the "Multi-Channel Pricing" slot the original architecture assessment reserved (0027–0031) but never filed until this sprint actually needed it — rejects modeling a Sales Channel as a MenuCategory. ADR-0041 rejects modeling the POS↔channel relationship as a fixed column on `SalesChannel`, keeping it per-entry on `SalesChannelEntry` instead so arbitrary POS/channel topologies are representable without a schema change per restaurant. ADR-0042 extends the same pattern to `SalesPaymentMethodEntry` and fixes a gap ADR-0041 left in place — both entry types' unique constraints now include `posSourceId`, so the same channel or payment method can be split across multiple POS terminals on the same business day, not only across different days.
