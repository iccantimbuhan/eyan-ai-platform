## Restaurant Onboarding Workflow (Sprint 1.4)

Populating a new restaurant's real master data is a one-time, manually-run seed script — not a UI workflow, not an OCR/AI importer (that's an explicitly deferred future sprint, built only after Inventory). The process, as run for Burger's Ink and Topo Gigio:

1. Gather real source material (photographed menus, photographed/forwarded supplier order sheets, any manually-typed ingredient lists) — real data only, never invented.
2. Transcribe menu items **verbatim**, including their printed ingredient descriptions where present. Items with only a name and price (no description) get a `MenuItem` row but deliberately **no `Recipe`** — "enough information exists" (this sprint's own bar) means a real ingredient list, not just a name.
3. Normalize ingredient names across sources (fix obvious misspellings, merge case/spelling variants — e.g. "Mozarella"/"Mozzarella" → one row) and strip purchase-pack-size suffixes ("25KG", "1KG") out of the name — pack size is a purchasing concern, not the ingredient's identity (ADR-0037).
4. Build Suppliers from the real order sheet, and link each Ingredient to every Supplier the source data actually shows it under — **do not assume one ingredient has one supplier**; the same real order sheet can (and did, for Burger's Ink's "Frying Oil") show one ingredient sourced from multiple suppliers.
5. **Do not seed `Unit` rows.** Units are restaurant-specific and entered manually through the UI by restaurant staff who know their own purchasing/recipe units. Since `RecipeIngredient.unitId` is a required foreign key, this means **no `RecipeIngredient` rows can exist until Units are entered** — that's expected, not a bug. A `Recipe` container can still be created (its `notes` field documents that lines are pending).
6. Never invent a quantity, weight, cost, or food-cost percentage that isn't in the source data. If it's not written down, it's not in the seed.
7. Write the script as idempotent find-by-`(restaurantId, name)`-then-create (same pattern as `seed-restaurant-tenancy.ts`) — safe to re-run, and this is what structurally prevents duplicate menu items/ingredients/suppliers/recipes, rather than a separate manual check.
8. Run once via `npx tsx prisma/seed-restaurant-product-onboarding.ts` against the target database — **not** wired into `bootstrap.ts`'s automatic deploy chain (real customer data isn't platform-required scaffolding, same "manual only" posture as `seed-demo-content.ts`).

Source data for Burger's Ink/Topo Gigio: `/home/eyancantimbuhan/Data Photos/` (photographed menus + the real "ORDER LIST BURGERS INK PAOLA" supplier sheet — outside the repository, not committed, since it's real customer material) plus a manually-provided, already-normalized Topo Gigio ingredient list.

## Tenant hierarchy

`Organization → Restaurant → Branch`. `Organization` is the one reusable tenant/membership/billing root (a future non-restaurant module would hang off the same primitive). `Restaurant` (a brand, e.g. Burger's Ink) and `Branch` (a physical location) are this module's own domain vocabulary beneath it — not platform-level.

Business data splits by ownership level, per the approved domain model (not uniformly Branch-scoped): **Menu** (`MenuCategory`, `MenuItem`) and **product knowledge** (`Ingredient`, `IngredientCategory`, `Supplier`, `Unit`, `Recipe`, `RecipeIngredient` — Sprint 1.3, ADR-0037) are **Restaurant-scoped**, since these are brand-level facts true at every Branch identically; **Inventory** (`InventoryItem`, `StockMovement` — Sprint 2A, ADR-0038) is **Branch-scoped** — it consumes the product catalog per-Branch (how much is on hand *here*) but never owns or redefines it. Purchases/Expenses/Daily Closing/Sales/Reports (Sprint 2B/3+) will also be Branch-scoped. Whichever level a table belongs to, every repository query against it must filter by that id — no exceptions, see Rules below.

## Inventory Foundation (Sprint 2A)

`InventoryItem` (one row per `(branchId, ingredientId)`, unique-constrained) tracks `currentQuantity`/`minimumQuantity` for an Ingredient at a Branch. `StockMovement` is a separate, append-only audit ledger (`OPENING_STOCK`/`ADJUSTMENT`/`WASTE`/`STOCK_COUNT`) — `currentQuantity` is a running balance updated only inside the same transaction as the movement that justifies it (`stock-movement.repository.ts`'s `record()`), never independently, so it structurally can't drift from the ledger or be silently mutated without history. Stock status (`IN_STOCK`/`LOW_STOCK`/`OUT_OF_STOCK`) is computed server-side from the two quantities on every read, never stored.

Creating an `InventoryItem` *is* recording opening stock — there's no separate "create then set opening stock" step, and opening stock can only be set once, at creation. Adjustments accept a signed delta; waste accepts a positive quantity the service negates; stock counts accept the absolute physical count and the service computes the delta against the current system quantity. Negative `currentQuantity` is allowed (not clamped) — see ADR-0038 Decision 4.

Reads (list/detail/movement history) are open to any `BranchMember` role. Writes (opening stock, minimum-threshold update, adjustment, waste, stock count) require `requireTenantRole('OWNER', 'MANAGER', 'SUPERVISOR', 'INVENTORY_STAFF')` — `CASHIER`/`KITCHEN`/`ACCOUNTANT`/legacy `STAFF` can view but not mutate. First real usage of the `INVENTORY_STAFF` role. Access itself is gated by a new `createBranchScopedAccessGuard` factory (`requireInventoryItemAccess`) — the Branch-first counterpart to `createRestaurantScopedAccessGuard`, walking the same three-tier chain `requireBranchAccess` already implements. See ADR-0038.

Explicitly out of scope for Sprint 2A (deferred to Sprint 2B/3): automatic stock deduction from `RecipeIngredient` quantities on a sale, purchase-driven stock increases, food costing, actual-vs-theoretical variance.

## Product Foundation (Sprint 1.3)

`Ingredient` optionally belongs to one `IngredientCategory` (soft grouping — deleting a category un-categorizes its ingredients via `SetNull`, unlike Menu's ownership cascade) and links to many `Supplier`s via the `IngredientSupplier` join table (many-to-many, no pricing yet — confirmed necessary by Burger's Ink's real order sheet, where "oil" is sourced from two different suppliers). `Unit` is a Restaurant-scoped, configurable unit-of-measure master list (g/kg/piece/...), not hardcoded.

`Recipe` belongs to exactly one `MenuItem` (`menuItemId` unique — enforced at the service layer with a pre-check, `MenuItemAlreadyHasRecipeError`, not just the DB constraint) and owns a list of `RecipeIngredient` lines (`ingredientId`, `unitId`, `quantity`, unique per `(recipeId, ingredientId)`). This is pure product-knowledge data — no stock deduction, no Inventory linkage; Inventory (Sprint 2+) will read this catalog, never own it.

An Ingredient's linked Suppliers are written via `supplierIds: string[]` on the same create/update call — the full set is replaced on write, mirroring `roles.service.ts`'s `updateRolePermissions` pattern, not a separate attach/detach endpoint.

All six new tenant-access guards (`requireUnitAccess`/`requireIngredientCategoryAccess`/`requireSupplierAccess`/`requireIngredientAccess`/`requireRecipeAccess`/`requireRecipeIngredientAccess`) share one `createRestaurantScopedAccessGuard` factory in `tenant.middleware.ts` — all six resources denormalize `restaurantId` directly onto the row (same posture as `MenuItem`), so the guard shape is identical across all of them; factored out to avoid six copy-pasted implementations.

## Two authorization axes — never conflate them (ADR-0036)

- **Platform RBAC** ("what modules can this user access at all") — the existing global `Role`/`Permission` system, completely unchanged in mechanism. Commercial customer users hold exactly one platform Role, `Restaurant Customer`, granted only the `restaurant` Permission — this alone hides AI Core/CRM/Finance/Content Studio/Administration from them via the same `useCan()`/`useModuleEnabled()` nav gating every other module already uses.
- **Tenant Role** ("what can this user do inside a Restaurant") — `TenantRole`, now seven named roles: `OWNER`, `MANAGER`, `SUPERVISOR`, `CASHIER`, `KITCHEN`, `INVENTORY_STAFF`, `ACCOUNTANT` (plus legacy `STAFF`, kept for Postgres compatibility, never assigned going forward). Enforced by `requireTenantRole(...roles)` in `tenant.middleware.ts`.

## Membership

Three independent junction tables, all `(userId, scopeId, role: TenantRole, assignedAt)`, composite-keyed, no separate id: `OrganizationMember` (access to every Restaurant/Branch under the Organization), `RestaurantMember` (scopes to one Restaurant, never its siblings), `BranchMember` (scopes to one Branch — added Sprint 1.2, amending ADR-0025's earlier YAGNI call now that a real customer needs it). A user can legitimately hold multiple grants at once (e.g. `RestaurantMember` on two of three restaurants).

**Effective role resolution is most-specific-wins**: a direct `BranchMember` role is used if present, otherwise the `RestaurantMember` role for the resolved restaurant, otherwise the `OrganizationMember` role for the resolved organization. This is what `requireTenantRole` computes (via `req.tenantContext`, populated by whichever tenant-access guard ran first in the chain — no extra query) and what `organization.mapper.ts`'s `myRole` fields mirror for frontend display.

Bootstrap seeding (`seed-restaurant-tenancy.ts`) still grants `OrganizationMember(OWNER)` to every user who already holds the platform's global `Owner` role — unchanged since Sprint 0. Onboarding real staff is Sprint 1.2's Staff Management feature.

## Staff Management (Sprint 1.2)

`StaffMembershipService` — one upsert method (`upsertMembership`) serves Invite/Assign Role/Assign Restaurant/Assign Branch identically, differing only in which scope is targeted; inviting a brand-new email creates the `User` (+ grants `Restaurant Customer`, additive, never touches an existing broader Role) and requires a name+password (no email-invite channel exists — ADR-0034 deferred Email); inviting an existing email just adds/updates a grant. "Disable Staff" hard-deletes every membership row under that Organization — deliberately not a reuse of `User.isActive`, which is global and would incorrectly lock a multi-tenant user out of unrelated Organizations. Takes effect on the user's next request (`authenticate()` reloads memberships fresh every time, no stale-JWT window).

Two route surfaces, same service underneath: `/organizations/:organizationId/staff` (`requireOrganizationAccess`) and `/restaurants/:restaurantId/staff` (`requireRestaurantAccess`, restaurant-scoped-only Managers aren't locked out; can only grant `RESTAURANT`/`BRANCH` scope, never `ORGANIZATION`). Both gated by `requireTenantRole('OWNER', 'MANAGER')`. Frontend currently only calls the Organization-scoped path (`/app/restaurant/staff`) — the Restaurant-scoped one exists on the backend for a future enhancement, not wired to a page yet.

## Rules

- **Every Restaurant repository query must filter by `branchId`/`restaurantId` — no exceptions.** This is the opposite of Finance/CRM's precedent (`.context/finance.md`, `.context/crm.md`): those are deliberately global shared workspaces with no per-row filtering.
- `requirePermission("restaurant")` gates *whether* a user can use the module at all; `requireRestaurantAccess`/`requireBranchAccess`/`requireOrganizationAccess`/`requireMenuCategoryAccess`/`requireMenuItemAccess` gate *which* Organization/Restaurant/Branch/Menu Category/Menu Item they can act on; `requireTenantRole` (composed after one of those) gates *what they can do* once there. All three layers, always — never skip one.
- A client-supplied foreign key into a sibling tenant-scoped table (e.g. `MenuItem.menuCategoryId`, `StaffMembership.restaurantId`/`branchId`) is never trusted without re-verifying it belongs to the already-authorized parent — see `MenuCategoryMismatchError`/`StaffScopeMismatchError`. A route's tenant-access guard only proves the id *in the URL* is authorized; it says nothing about IDs inside the request body.
- `requireTenantRole` must always be composed *after* a tenant-access guard on the same route — it reads `req.tenantContext`, which only that guard populates, and fails closed (denies) if it's missing.
- The Module Registry (`OrganizationModule`, gated via `useModuleEnabled()`) and the `Restaurant Customer` platform Role both control nav/route *visibility* only. Neither is the real enforcement — `requirePermission`/`requireRestaurantAccess`/`requireBranchAccess`/`requireTenantRole` are.
- **Known gap, partially resolved in Sprint 2A**: Branch-scoped-only staff (Cashier/Kitchen/Supervisor/Inventory Staff, no Restaurant/Organization membership) still cannot reach Menu Category/Item routes or the Sprint 1.3 Ingredient/Recipe/Supplier/Unit routes — those are unchanged, still gated by `requireRestaurantAccess`/`createRestaurantScopedAccessGuard`, neither of which considers `BranchMember`. Inventory (Sprint 2A) is the first domain that closes this for itself: it's genuinely Branch-scoped, uses `createBranchScopedAccessGuard`/`requireInventoryItemAccess` (which does consider `BranchMember`, at tier 1), and pairs it with a read/write `requireTenantRole` split. See ADR-0036/0037's Consequences for the still-open part, ADR-0038 for the resolved part.
- **Real customer data now exists in the dev database** (Sprint 1.4, both restaurants) — treat `eyan_ai_platform_dev`'s Ingredient/Supplier/MenuItem/Recipe rows as real, not disposable test fixtures. Sprint 2 work (and any future ad-hoc dev-DB testing) should create its own throwaway rows rather than mutating or deleting this onboarded data; the `seedRestaurantProductOnboarding` script is idempotent and safe to re-run if it's ever accidentally cleared.
- Do not reuse `Finance.Expense` for restaurant expenses when that module ships (Sprint 3) — same word, unrelated domain and tenancy model. Do not route Slack (Sprint 7) through `eyan-automation-hub` — see ADR-0034.
- Master-data list endpoints (Restaurant/Branch/Menu Category/Menu Item/Staff) are deliberately unpaginated — realistic row counts per restaurant don't warrant Finance Expense's pagination machinery yet.
