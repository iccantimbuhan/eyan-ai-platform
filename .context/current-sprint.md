**Restaurant Operations Platform — Cash Reconciliation — Amendment: Cash/Electronic Discount Split — complete.** The manager reported a second, distinct problem on top of the POS-scoping amendment below: their POS can't record a discount against the actual amount received at all, so staff enter one combined `discountsTotal` figure covering both a cash-reducing portion and an electronic/card-reducing portion together (e.g. €61.35 = €49.45 cash + €11.90 electronic), and the formula was subtracting the *entire* combined figure from physical cash, overstating the shortfall. Explicitly not a platform-wide rule — most restaurants never touch it; stays entirely restaurant-configurable, never hardcoded by payment-method or POS-source name. One more additive nullable column, `DailySalesRecord.cashDiscountTotal` — `null` means "not configured," reproducing the pre-amendment formula (the full `discountsTotal` reduces cash) byte-for-byte for every existing record, zero backfill, zero invented allocation. `computeCashReconciliation()` now derives `cashReducingDiscount = cashDiscountTotal ?? discountsTotal` and uses that everywhere cash is reduced, composing unchanged with the existing POS-scoping rule; `electronicDiscountTotal` is computed only for display (shown next to Card/Electronic payment methods), never subtracted from cash, never a second stored source of truth. Also fixed during inspection: `SalesAggregationService`'s weekly `totalExpectedCash` was re-derived from `totalPhysicalCashBasis - discountsTotal` rather than accumulated from each day's own computed `expectedCash` — would have silently ignored the electronic-discount portion at the weekly level too; now accumulates per-day so daily and weekly can never drift apart. `DailySalesDialog` gained an optional "Cash Discount (optional)" field; `CashReconciliationCard` now shows "Cash Discount Applied" (the correct, reduced figure) under the discounted POS bucket plus a new "Electronic Discount" line next to Card/Electronic payment methods. Three additive migrations total now (`isCashEquivalent`/`actualCashCounted`, then `discountPosSourceId`, then `cashDiscountTotal`). Verified: 1213/1213 backend tests pass (15 new), 495/495 frontend tests pass (1 new), both typecheck clean, lint clean, both builds succeed. Live smoke test against the real dev database (temporary, distinctly-named payment-method rows — never touching the restaurant's real configured catalog) reproduced the manager's exact worked numbers end to end via the real service layer (physical cash €374.18, cash discount applied €49.45 not the full €61.35, electronic discount €11.90 shown separately, expected cash €324.73, BALANCED), 12/12 checks passed, exact baseline row-count restoration after cleanup. See ADR-0043's second amendment section.

**Also complete — Restaurant Operations Platform Sprint 2D (Sales Reporting & Analytics Foundation).** Turns Sprint 2C's raw daily sales records into management reporting the manager can use in place of the weekly Excel report's analytical purpose — **zero schema changes**, everything computed fresh on read by extending the existing `SalesAggregationService` and `daily-sales-record.mapper.ts`.

Five additions, all pure computation over Sprint 2C's existing tables: (1) **Data coverage** — `daysInRange`/`daysRecorded`/`missingDays`/`missingDates[]`/`averageSalesPerRecordedDay`, computed by enumerating every calendar date in the requested range and diffing against dates with an actual `DailySalesRecord`; a day with no record is never treated as €0, anywhere. (2) **Breakdown percentages** — each channel/payment-method/category's share of that breakdown's *own* recorded total (never a share of `totalSales`, which isn't guaranteed to reconcile with any breakdown per ADR-0039 Decision 2); `null` when the breakdown's own total is zero. (3) **Channel performance** — `activeDays` + `averageAmountPerActiveDay` per channel, with the frontend labeling the top channel by amount/average using neutral wording ("Highest recorded sales" / "Highest average sales/day"), never "best channel." (4) **Reconciliation** — `totalSales` vs. `posReportedTotal` vs. `channelEntriesTotal` and their variances, surfaced (never auto-corrected, never labeled an error) on both the weekly summary and — new this sprint — the single-day response via a `reconciliation` field added to `DailySalesRecordResponseDto`. (5) **Explicit two-period comparison** — `GET /branches/:branchId/sales/comparison?currentStartDate=&currentEndDate=&previousStartDate=&previousEndDate=`; both periods are supplied by the caller, the backend never infers "the previous period"; `changePercent` is `null` (never `Infinity`/`NaN`) when the previous period's value is zero, rendered as "No comparison data" by the frontend.

A `SalesTrendChart` (recharts — already a project dependency, used by Finance/CRM dashboards, no new library added) plots only recorded days; a missing day has no bar at all rather than a zero-height one.

Endpoints: `GET /branches/:branchId/sales/comparison` (new) alongside Sprint 2C's existing `/sales`, `/sales/daily`, `/sales/weekly`, `/sales/:salesId`. Same authorization as Sprint 2C throughout — reads gated only by `requireBranchAccess`/`requireSalesRecordAccess`, no new role list needed since reporting is read-only.
