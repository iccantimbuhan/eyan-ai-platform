**Restaurant Operations Platform — Sprint 2A (Inventory Foundation) — complete.** Branch-scoped current stock, opening stock, manual adjustment, waste, physical stock count, and a full movement audit trail — built on the Sprint 1.3 product catalog (Ingredient/Unit) without modifying it, per ADR-0037's boundary. New Prisma models `InventoryItem` (`@@unique([branchId, ingredientId])`, `currentQuantity`/`minimumQuantity`) and `StockMovement` (append-only ledger: `OPENING_STOCK`/`ADJUSTMENT`/`WASTE`/`STOCK_COUNT`, signed `quantityDelta`, `quantityAfter` snapshot). `currentQuantity` is a running balance updated only transactionally alongside its justifying movement — structurally impossible to change without an audit row. Stock status (`IN_STOCK`/`LOW_STOCK`/`OUT_OF_STOCK`) is computed server-side on every read, never stored. See ADR-0038.

New `createBranchScopedAccessGuard` factory in `tenant.middleware.ts` (`requireInventoryItemAccess`) — the Branch-first counterpart to the existing `createRestaurantScopedAccessGuard`, walking the same three-tier Branch→Restaurant→Organization chain `requireBranchAccess` already implemented. Because Inventory is genuinely Branch-scoped from day one, this closes the ADR-0036/0037-documented "Branch-scoped-only staff can't reach Restaurant-scoped routes" gap **for Inventory specifically** — Ingredient/Recipe/Supplier/Unit routes are unchanged and still have the gap. Reads are open to any branch role; writes (opening stock, minimum-threshold update, adjustment, waste, stock count) require `requireTenantRole('OWNER', 'MANAGER', 'SUPERVISOR', 'INVENTORY_STAFF')` — confirmed with the user before implementation — the first real usage of the `INVENTORY_STAFF` role reserved since Sprint 1.2.

Endpoints: `GET/POST /branches/:branchId/inventory-items` (nested, mirrors Ingredient/Recipe), `GET/PATCH /inventory-items/:id`, `GET /inventory-items/:id/movements`, `POST /inventory-items/:id/{adjustments,waste,stock-count}` — three separate self-documenting write endpoints rather than one with a `type` discriminator. Every client-supplied `ingredientId`/`unitId` is re-verified against the branch's restaurant before write (`InventoryScopeMismatchError`), mirroring `RecipeIngredientService`'s existing defense-in-depth pattern.

Frontend: new `Inventory` page under Restaurant Operations (Branch `<Select>`, a new pattern one level below the existing Restaurant `<Select>`), a table with computed status badges, and five dialogs (Add Inventory Item/opening stock, Edit Minimum Threshold, Adjustment, Waste, Stock Count) plus a movement-history side panel — all following the existing restaurant-ops file-shape and shadcn form conventions exactly. `useActiveTenant()` extended to also resolve `branchId`/`branches` (the underlying `activeBranchId`/`setActiveBranch` tenant-store state existed since Sprint 0 but was never surfaced to pages until now). Write actions are hidden client-side for roles outside the write policy (display-only, backend is the real enforcement).

Verified: 1058/1058 backend tests pass (34 new — service-layer create/adjust/waste/count math including the spec's own worked examples, the new branch-scoped guard's full tier/cross-tenant/cross-branch matrix, and a dedicated write-role-split permission test), 422/422 frontend tests pass (4 new), both typecheck clean, frontend production build succeeds. Live smoke test against the dev database (real HTTP, real JWTs, a temporary Unit/InventoryItem and a temporary CASHIER `BranchMember` grant, all cleaned up afterward) confirmed: opening stock → adjustment → waste → stock count produces the exact expected running balance at every step, movement history returns in correct order, duplicate branch+ingredient creation 409s, cross-restaurant ingredient/unit scope mismatch 400s, unauthenticated requests 401, and a real `BranchMember`-only CASHIER account can read but is correctly rejected (403) from every write action. Sprint 1.4's real onboarded data (149 Ingredients, 68 Recipes, 17 Suppliers across both restaurants) confirmed untouched throughout.

Explicitly **not** built (Sprint 2B/3+, per this sprint's own scope): automatic stock deduction from `RecipeIngredient` quantities when a menu item sells, purchase-driven stock increases, food costing, actual-vs-theoretical variance, `DELETE /inventory-items/:id`.
