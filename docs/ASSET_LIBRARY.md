# Asset Library & QA Workflow

Sprint 5 adds a management layer on top of Content Studio's existing generation features: an **Asset Library** (browse, search, filter, and batch-act on everything generated in a project) and a **QA review workflow** (Draft → Needs Review → Approved/Rejected → Published, with a checklist, reviewer notes, and a per-project Review Queue). Generation still happens exactly where it always did — the Content and Images tabs are unchanged. Management happens in two new tabs: **Assets** and **Review**.

This document covers the architecture and how to extend it. For the feature list itself, see the sprint log (`tasks/completed/sprint-5-asset-library-qa.md`).

---

## The core design problem

Before this sprint, generated output lived in two independent tables — `GeneratedContent` and `GeneratedImage` — each with its own repository/service/controller, and no shared concept of "an asset." Adding review status, a checklist, and version history for both (and for a third source, project-scoped prompt templates) without redesigning either existing table was the central constraint. See ADR-0008 for the full decision record; this section summarizes the shape.

**`AssetType`** is a new enum whose first five values mirror `ContentType` exactly (`BLOG`, `EMAIL`, `SOCIAL_MEDIA`, `MARKETING_COPY`, `DOCUMENTATION`), plus `IMAGE` and `PROMPT_TEMPLATE` — the two other real asset sources. A `GeneratedContent.type` value casts straight to `AssetType`; no mapping table exists or is needed.

**`AssetReview`** and **`AssetVersion`** are two new, purely additive tables — neither `GeneratedContent` nor `GeneratedImage` gained a new column for either concern. Both are keyed on `(assetType, sourceId)`, where `sourceId` is the id of the underlying `GeneratedContent` / `GeneratedImage` / `SavedPrompt` row. An asset with no `AssetReview` row is implicitly `status: DRAFT`; an asset with no `AssetVersion` row is implicitly `version: 1`. Both rows are created lazily — the first time an asset is actually reviewed or regenerated — never eagerly at generation time.

**`SavedPrompt.projectId`** (nullable) is the one existing table that did change. `null` means a global, reusable prompt — the original behavior, still exactly what the standalone Prompt Library page shows via `GET /saved-prompts`. A non-null value scopes the prompt to a project, making it a real `PROMPT_TEMPLATE` asset in that project's Asset Library. There is no dedicated creation UI beyond the Asset Library's "New Prompt Template" button (which reuses `SavePromptDialog` with a `projectId` prop) — there is no automatic migration of existing global prompts into any project.

**`generationTimeMs`** (nullable) was added directly to `GeneratedContent` and `GeneratedImage` — the one exception to "no columns on the existing tables." Asset Details requires showing how long a generation took, and that value cannot be reconstructed after the fact; it's captured by timing the existing `provider.generate()` / `chatService.chat()` call in `ContentService.generate()` / `ImageService.generate()`. No control flow or error handling in either method changed.

## Aggregation: how `GET /assets` actually works

`AssetService.list()` does **not** run one query. It fetches up to 500 rows from each relevant source in parallel (`ContentRepository.findMany`, `ImageRepository.findMany`, `SavedPromptRepository.findManyByProject` — skipping a source entirely if the `type` filter excludes it), maps each row to a common `AssetSummaryDto` via `asset.mapper.ts`, batch-fetches review/version rows for all of them in two more queries (`assetReviewRepository.findManyBySourceIds` / `assetVersionRepository.findManyBySourceIds`), merges the results, then applies `search`/`status`/`provider`/`model` filters, sorts, and paginates **in application code**.

This is a deliberate, documented scope boundary: fine at demo/portfolio data volumes (dozens to hundreds of assets per project), not intended to scale to a real production catalog without moving to a database-level `UNION ALL` (or a materialized view). If that becomes necessary, `AssetService.list()` is the only place that needs to change — the DTO shape, the controller, and every frontend consumer are unaffected.

## Adding a future asset type

The brief explicitly calls for this to be possible "without refactoring." The recipe:

1. Add the new value to the `AssetType` enum in `schema.prisma`; run a migration.
2. Add a `mapXToSummary()` / `mapXToDetail()` pair in `asset.mapper.ts`, following the existing pairs' shape.
3. Add the new source's repository to `AssetService`'s constructor, and one more branch in `list()`'s parallel fetch, `findSource()`'s dispatch, `toDetailDto()`'s switch, `providerOf()`/`modelOf()`, and (if applicable) `regenerate()`/`duplicate()`/`delete()`.
4. Route the new type to the right `ChecklistCategory` in the frontend (`checklistCategoryForAssetType()`, `types/asset.ts`) and add an `AssetTypeIcon` branch (`AssetCard.tsx`).

No existing model, endpoint, or frontend component needs to change shape — only new cases are added to a small number of switches.

**This recipe is no longer hypothetical — it has now shipped twice.** Sprint 6.1 (Brand Kits) followed it for `AssetType.BRAND_KIT`: `mapBrandKitToSummary()`/`mapBrandKitToDetail()`, a `brandKit` branch in every `AssetService` switch, and a reachable frontend tab. It's also the first asset type where regeneration is explicitly unsupported for a reason other than "it's user-authored text" — a `BrandKit` is guidance data, not generated output — reusing the exact same `AssetActionNotSupportedError` path `PROMPT_TEMPLATE` already established.

Sprint 6.2 (AI Video Studio) followed it for `AssetType.VIDEO`, with one added wrinkle: a single new `VideoAsset` table covers **eight** different artifact kinds (`VideoAssetKind`: `SCRIPT`, `SCENE_BREAKDOWN`, `SHOT_LIST`, `VOICE_OVER_SCRIPT`, `CAPTIONS`, `SUBTITLES`, `STORYBOARD`, `THUMBNAIL`) under one `AssetType` value — the first asset type where the underlying table itself branches internally (text-kind rows populate `output`/`model`, exactly like `GeneratedContent`; image-kind rows populate `provider`/`storagePath`/`status`, exactly like `GeneratedImage`), rather than every row in the table being structurally uniform. Unlike Brand Kits, a `VideoAsset` **is** provider/AI-generated (both kinds), so `regenerate()` is supported for it — the first non-content, non-image asset type where that's true. See `tasks/completed/sprint-6-1-brand-kits.md` and `tasks/completed/sprint-6-2-ai-video-studio.md` for the full implementations.

## Creative Review Workspace (Sprint 6.3)

Sprint 6.3 extends the review system itself rather than adding a new asset type — three new tables, all keyed on `(assetType, sourceId)` exactly like `AssetReview`/`AssetVersion`, all purely additive, none touching `GeneratedContent`/`GeneratedImage`/`VideoAsset`/`BrandKit` shape. Full rationale in ADR-0009.

- **`AssetComment`** — general comments and annotations, unified in one table. A row with no anchor (`regionX/Y/Width/Height`, `timestampMs`) is a general comment; a row with `regionX/Y/Width/Height` set is an image-region annotation (normalized 0–1 floats); a row with `timestampMs` set is a video-artifact annotation (a manually-entered logical marker in milliseconds — no real video file exists to sync playback against, the same limitation already documented for `VideoAsset`'s `SUBTITLES`/`CAPTIONS` kinds). `isInternal` marks a comment as reviewer-only. `resolvedAt`/`resolvedBy` track resolution.
- **`AssetReviewAssignment`** — records who is intended to review an asset. **Informational only**: it does not grant the assignee access to the project. `ContentProject` remains single-owner (ADR-0007), unchanged by this sprint. One active assignment per asset; assigning again replaces it.
- **`AssetReviewEvent`** — an append-only activity log (never updated or deleted except cascade on project delete), one row per review-relevant action: `STATUS_CHANGED`, `COMMENT_ADDED`, `COMMENT_RESOLVED`, `ANNOTATION_ADDED`, `ASSIGNED`, `UNASSIGNED`, `VERSION_CREATED`. Fed as a side-effect from `AssetService.review()`/`regenerate()` and the new comment/assignment methods. Note: `VERSION_CREATED` is written against the **new** source id produced by a regeneration, not the old one — the old asset's timeline stops at whatever status change triggered the regeneration; the new asset's timeline starts with `VERSION_CREATED`.

`ReviewStatus` also gained one new value, `REVISION_REQUESTED` — an additive enum growth (existing rows keep their value), sitting alongside `NEEDS_REVIEW`/`APPROVED`/`REJECTED` as another terminal-ish review outcome that a reviewer sets manually via the same `PATCH .../review` endpoint every other status transition already uses. The frontend's "Request Revision" flow is two independent API calls from one button — create a comment with the reason, then set the status — matching how `AssetDetailSheet` already composes several independent mutations rather than the backend offering one combined action.

`AssetSummaryDto`/`AssetDetailDto` gained `commentCount`, `openCommentCount`, and `assignee` fields, batch-fetched in `AssetService.list()`/`getDetail()` the same way review/version are already batched — no new round trip per card in the Asset Library or Review Queue.

## Publishing Pipeline (Sprint 6.4)

Sprint 6.4 adds a **Publishing Pipeline**: the ability to take an approved asset and publish it to an external platform. It is a deliberately independent workflow from QA review, not a stage of it — full rationale in ADR-0010.

- **`PublishingRecord`** — one new, purely additive table, one row per `(assetType, sourceId, platform)` triple (`@@unique`, upsert-style like `AssetReviewAssignment`, not append-only). Owns its own `PublishingStatus` lifecycle (`DRAFT → SCHEDULED → PUBLISHING → PUBLISHED`, or `→ FAILED`, or `→ ARCHIVED`) — entirely separate from `ReviewStatus`, which stays QA-only and untouched. Scheduling/publishing an asset requires its current `AssetReview.status` to be `APPROVED`, checked in `AssetService` at call time (a service-layer gate, not a database constraint, since the two tables are intentionally independent).
- **Platform provider abstraction** — mirrors `ImageProviderFactory`'s `Map`-based registry (`PlatformProviderFactory.register`/`create`/`listRegistered`/`reset`), not `ProviderFactory`'s single-hardcoded-provider shape (ADR-0001), because real publishing targets (Facebook, Instagram, LinkedIn, TikTok, YouTube, WordPress, ...) are known future candidates. Only `"fake"` (`FakePlatformProvider`) is registered today — deterministic, no network calls, same purpose as `FakeImageProvider`: exercising the full pipeline end-to-end before any real, billable integration exists. Adding a real platform later is one new class + one `register()` call, no changes to `AssetService` or any route.
- **Timeline reuse, not a second timeline** — every publishing action (`schedulePublish`, `publish`, a provider failure) writes to the existing `AssetReviewEvent` table via four new `ReviewEventType` values (`PUBLISH_SCHEDULED`, `PUBLISH_STARTED`, `PUBLISHED`, `PUBLISH_FAILED`), so the Review Timeline UI shows publishing activity interleaved with QA activity for free. Archiving a record is administrative bookkeeping and deliberately does **not** grow the enum further or write an event.
- **Scheduling is persisted intent only** — confirmed scope decision, see ADR-0010. No queue, cron, or background worker exists in this codebase; `scheduledFor`/`status: SCHEDULED` just records when a user *intends* to publish. Nothing executes it automatically. `AssetService.publish()` is the single, stable method that actually calls the provider — designed so a future background executor can call it unchanged once one exists, but this sprint only calls it from the immediate "Publish Now" action and from `retryPublish()`.
- **Failure handling mirrors `ImageService.generate()`'s existing convention** — a provider (or provider-lookup) failure is caught, persisted durably (`status: FAILED`, sanitized `errorMessage`, incremented `attempts`), and a generic error is thrown to the client; the raw error never reaches the HTTP response. Retry is user-initiated only (`retryPublish()`, allowed only from `FAILED`) — no automatic retry-with-backoff.
- **`AssetSummaryDto`/`AssetDetailDto` gained `publishing: { platform, status }[]`**, batch-fetched in `AssetService.list()`/`getDetail()` alongside review/version/comments/assignment — the same in-memory aggregation pattern every prior addition to this DTO has used. `GET /assets` also gained an optional `publishingStatus` filter, applied in-memory after aggregation like every other list filter.
- **`PublishingQueue` is a new, separate frontend component from `ReviewQueue`**, not a merged tab bar — QA and Publishing are two independent but connected workflows, kept visually distinct even though both are built on the identical `useAssets(projectId, filters)` list endpoint and `AssetSummary` data.

## Analytics Foundation (Sprint 6.5)

Sprint 6.5 adds the data and query layer Sprint 6.6's Production Dashboard visualizes — backend-only this sprint (matching the precedent Sprint 4.1 already set: a complete backend pipeline shipped before any frontend existed for it). Full rationale in ADR-0011.

- **Almost nothing new to store.** Review workflow, approval metrics, publishing, publishing performance, brand kit usage, provider usage, and generation duration are all answered by *querying* existing tables (`AssetReview`, `AssetReviewEvent`, `PublishingRecord`, and the `provider`/`model`/`generationTimeMs`/`brandKitId` columns already on `GeneratedContent`/`GeneratedImage`/`VideoAsset`) — a new read-only `AnalyticsService` composes these, aggregating in the service layer the same way `AssetService.list()` already does (ADR-0008), not via raw SQL rollups.
- **`AnalyticsEvent`** — the one genuine gap: a first-time generation writes zero event/log row anywhere today (`AssetReviewEvent` is only entered once an asset is touched by the QA workflow). One new, purely additive, append-only table, same polymorphic `(assetType, sourceId)` shape as `AssetReviewEvent`, written once per generation from `ContentService`/`ImageService`/`VideoAssetService.generate()`. Deliberately a *separate* table from `AssetReviewEvent`, not a new `ReviewEventType` value, to keep that table's review-scoped purpose (ADR-0009) intact and avoid coupling the plain generation services to the review/versioning layer. `provider`/`model`/`generationTimeMs`/`brandKitId` are real columns, not JSON, so provider-usage/generation-duration/brand-kit-usage aggregation can `groupBy`/average on them directly.
- **Genuinely fire-and-forget** — the analytics write is *not awaited* by the generation services, a first inside a request path in this codebase (the only prior unawaited pattern runs once at server boot). Unlike `ImageService.delete()`/`markFailed()`'s awaited-but-swallowed "best-effort" writes (which protect a real invariant — a user must always be able to delete something even if disk cleanup fails), there is no invariant requiring the analytics row to exist before the generation response returns, so it isn't awaited at all — just fired, with a `.catch()` that logs on failure. Verified directly in tests, not just asserted: `generate()` is confirmed to still resolve normally when the faked analytics write rejects.
- **`GET /api/v1/analytics/summary`** (across every project the requesting user owns) **and `GET /api/v1/analytics/projects/:projectId/summary`** return asset counts by type, review/publishing status counts (an asset with no `AssetReview` row is folded into an implicit `DRAFT` count, matching ADR-0008's "no row = DRAFT" convention), provider usage with average generation duration, brand kit usage, and review/publishing performance (average time from first `NEEDS_REVIEW`→`APPROVED`, and `PUBLISH_STARTED`→`PUBLISHED`, computed in-memory from `AssetReviewEvent` rows).
- **`GET /api/v1/analytics/projects/:projectId/activity`** merges `AnalyticsEvent` and `AssetReviewEvent` rows into one normalized, paginated feed, sorted newest-first — no second timeline, no duplicated event data.
- **No new RBAC gate** — `authenticate`-only, consistent with every other Content Studio route, even though unused `"analytics"`/`"dashboard"` permissions already exist in the seed data (see ADR-0011 for why).

## Production Dashboard (Sprint 6.6)

Sprint 6.6 builds the dashboard UI on top of Sprint 6.5's endpoints — almost entirely frontend work, no new database storage.

- **A dedicated Content Studio page, not the platform's home dashboard.** Confirmed with the user: the existing `/` dashboard is infrastructure/platform administration (system health, models, providers) for a different audience than Content Studio's creative operations. The Production Dashboard lives at `/content-studio/dashboard`, with its own "Production Dashboard" sidebar entry alongside "Content Studio" and "Prompt Library" — the platform's home dashboard is untouched.
- **One small, additive backend extension**: `GET /api/v1/analytics/activity` (platform-wide, across every project a user owns) — Sprint 6.5 only built the project-scoped version. `AnalyticsEventRepository.findManyByProjectIds()`/`AssetReviewEventRepository.findManyByProjectIds()` are the only two new repository methods (mirroring the existing `findManyBySourceIds`-style batch-by-IN-query shape already used elsewhere); `AnalyticsService.getPlatformActivity()` reuses the identical merge/sort/paginate logic `getProjectActivity()` already established, via a shared `buildActivityFeed()` helper.
- **One shared `AnalyticsSummary` component, reused unchanged in two places** — the backend returns the identical `ProjectAnalyticsSummaryDto` shape for both the platform-wide and per-project endpoints, so one composition (`assets-by-type` chart, `provider-usage` chart, review/publishing status lists, review/publishing performance stat tiles) renders both the Production Dashboard and the new per-project "Analytics" tab in `ProjectWorkspace`, with only the data source differing.
- **Charts follow the `dataviz` skill's procedure**: single-series magnitude bars (assets-by-type, provider usage) use one consistent color from this app's existing `--chart-1`/`--chart-2` theme tokens rather than inventing a new palette; average generation duration is a tooltip detail, never a second y-axis (no dual-axis charts); a handful of named review/publishing statuses are rendered as a labeled count list (reusing the same shadcn `Badge` variants `AssetStatusBadge` already established) rather than forced into a bar chart, since "sometimes the answer isn't a chart."
- **`recharts`** (already an installed, previously-unused dependency) is the first thing in this codebase to import it — required adding it to `vite.config.ts`'s `optimizeDeps.include` so the browser-mode test runner pre-bundles it instead of re-optimizing mid-test-run (which was duplicating the React instance and throwing "Invalid hook call").
- **`ReviewQueue`/`PublishingQueue` are not embedded** in either dashboard view — both are full, self-contained page sections with their own filter/pagination/detail-sheet chrome, not designed as tiles. The dashboards show their status-count summaries (already in the summary DTO) instead.

## What's client-side only, and why

**Downloads and exports never hit a new backend endpoint.** Images already have a real, downloadable file via the existing static serving (`resolveImageUrl()` + a `fetch()`-then-blob download, forcing the download even across origins in local dev); Markdown/JSON exports are built in the browser from data the app already fetched (`lib/asset-export.ts`). This was an explicit scope decision (see the requirements discussion): no archiver dependency, no streaming multi-file endpoint, nothing that isn't already fetchable.

**Duplicate behaves differently per asset type, and that's deliberate, not inconsistent:**
- Content: a direct database row copy (`ContentRepository.create()` with the same prompt/output/model) — instant, free, no provider call.
- Prompt template: a direct row copy (`SavedPromptRepository.create()`), name suffixed `" (Copy)"`.
- Image: **not** a file copy — there's no copy primitive on `StorageProvider`, and two `GeneratedImage` rows pointing at one stored file would make deleting either one corrupt the other. An image "Duplicate" re-generates a fresh copy from the same prompt/provider instead. It deliberately does not create a version link (a duplicate is an independent asset, not a new version of the one it was copied from) — that's what actually distinguishes it from Regenerate.
- Video asset (Sprint 6.2): follows whichever of the two rules above applies to its `kind` — a text-kind row (`SCRIPT`/`SCENE_BREAKDOWN`/`SHOT_LIST`/`VOICE_OVER_SCRIPT`/`CAPTIONS`/`SUBTITLES`) duplicates via a direct row copy like content; an image-kind row (`STORYBOARD`/`THUMBNAIL`) re-generates like an image, for the same file-copy-primitive reason.

**Version Compare is side-by-side, not a line-level diff.** The brief asks for "Compare," not a diff algorithm; each pane renders the full output/image for the selected version via the same `AssetDetail` shape the detail sheet already uses. **Version Restore is present but disabled** — explicitly future-ready per the brief, not wired this sprint.

**QA Score is a plain number field, not a computed one.** A reviewer can enter 0–100 manually via the QA panel; nothing calculates or validates it against the checklist. "Future-ready" per the brief means the field exists and is capturable, not that scoring is automated.

## Review Queue scope

The Review Queue is a tab inside `ProjectWorkspace`, not a global route — a deliberate choice from the requirements discussion, matching how a QA workflow was asked to ship this sprint. It is built on the exact same `useAssets(projectId, filters)` hook and `AssetSummary` data as the Asset Library tab; only the `status` filter and row density differ. The backend's `GET /assets` endpoint and `AssetService.list()` already accept `projectId` as a normal query parameter (not hardcoded into the route path), so promoting this to a global, cross-project queue later is a matter of relaxing `listAssetsValidator`'s `projectId` requirement and adding a new route — not a rewrite of the aggregation, review, or versioning logic.

## Frontend: why the data-table kit wasn't reused directly

`components/data-table/{toolbar,faceted-filter,pagination,bulk-actions}.tsx` already exist and are visually exactly what an "enterprise" search/filter/paginate/batch-select UI should look like — but every one of them is bound to a `@tanstack/react-table` `Table`/`Column` instance driving **client-side** filtering and pagination over already-loaded rows. The Asset Library filters and paginates **server-side** (`GET /assets?type=&status=&provider=&search=&page=`, each filter single-valued). Forcing that through `react-table`'s client-filtering abstraction would mean either lying to it (`manualFiltering: true` on a table whose whole API assumes it isn't manual) or maintaining a parallel, redundant source of truth.

Instead, `AssetToolbar`, `AssetPagination`, and `AssetBulkActionsBar` are purpose-built siblings — same visual language (same Tailwind classes, same Popover/Command/Badge composition, same floating bottom-center bulk-action bar), driven by plain props instead of a table instance. This is not a new architectural pattern; it's the same UI composition already established, adapted to the data flow this feature actually has.
