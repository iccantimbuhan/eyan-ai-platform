| 0034 | Automation & Communication Layer | **Proposed, not yet implemented.** Slack (and future WhatsApp/Telegram/Email) register as MCP connectors translating channel messages into calls against existing Services/Capabilities; explicitly not routed through the independent `eyan-automation-hub` repo. |
| 0035 | Deployment Bootstrap Strategy | Splits seed data into platform bootstrap (`bootstrap.ts` — roles, permissions, Restaurant tenancy foundation; idempotent, automated in `deploy.sh`) vs. demo/sample content (`seed.ts` — portfolio demo account, demo Content Studio project; stays manual, permanently). Fixes the exact gap that left the Sprint 0 Restaurant Operations sidebar hidden after deploy: seeding had only ever been a manual, forgettable step. |
| 0036 | Customer-Facing Authorization: Platform RBAC vs. Tenant Role Capabilities | One new platform Role (`Restaurant Customer`, granted only `restaurant`) hides internal modules from commercial customers with zero nav-gating changes. `TenantRole` expands to seven named roles + `BranchMember` (amends ADR-0025's YAGNI note — the customer it deferred on now exists). New `requireTenantRole` middleware, composed after the existing tenant-access guards, resolves the caller's effective role from data already loaded on `req.user` — no new query. First real usage: Staff Management (Invite/Disable/Assign Role/Restaurant/Branch), an upsert over the three membership tables. |
| 0037 | Restaurant Product Foundation: Domain Ownership Before Inventory | `Ingredient`/`IngredientCategory`/`Supplier`/`Unit`/`Recipe`/`RecipeIngredient` are all Restaurant-scoped (product knowledge is a brand-level fact) — Inventory (Sprint 2+) will be Branch-scoped and only ever manage stock against this catalog, never own it. Real Burger's Ink/Topo Gigio data validated the model before implementation, including the many-to-many Ingredient↔Supplier relationship (evidenced directly: "oil" sourced from two suppliers on the real order sheet). `Recipe` is data-only — no stock deduction yet. |
| 0038 | Inventory Foundation: Branch-Scoped Stock, Append-Only Ledger | `InventoryItem` (Branch-scoped current stock) + `StockMovement` (append-only audit ledger); `currentQuantity` is a running balance updated only transactionally alongside its justifying movement, never independently. Stock status is computed, never stored. A new `createBranchScopedAccessGuard` (mirrors `createRestaurantScopedAccessGuard`, walks `requireBranchAccess`'s chain) closes the ADR-0036/0037 Branch-staff access gap for this domain specifically; writes additionally require `requireTenantRole('OWNER','MANAGER','SUPERVISOR','INVENTORY_STAFF')` — first real use of `INVENTORY_STAFF`. |
| 0039 | Sales Foundation: Branch-Scoped Daily Records, Channel/Payment-Method Separation | `DailySalesRecord` (one per Branch per business day, `@@unique([branchId, businessDate])`) + `SalesChannel`/`SalesPaymentMethod`/`SalesCategory` (Restaurant-scoped configurable master lists, mirror `Unit`) + four line-entry child tables. Channel and payment-method totals are never reconciled against each other or against `totalSales`/`posReportedTotal` — stored exactly as entered. Itemized sales snapshot `itemName`/`categoryName`; `menuItemId` is an optional `SetNull` cross-reference only, so a later Menu edit can never corrupt sales history. Reuses `createBranchScopedAccessGuard` (ADR-0038) with no new authorization pattern; writes require `requireTenantRole('OWNER','MANAGER','SUPERVISOR','ACCOUNTANT')`. Weekly aggregation is computed on every read from raw records, never stored. Explicitly excludes recipe consumption, inventory deduction, purchasing, costing, POS integration, and WhatsApp/OCR/AI. |
| 0040 | Multi-Channel Menu Pricing: A Reference Table, Not a New MenuCategory | `SalesChannelMenuItem` — an optional `(SalesChannel, MenuItem)` override row (`price`/`available`), `@@unique` on the pair. `MenuItem.price` remains the one authoritative base price, never overwritten; a missing row means "use the base price on this channel." Never written onto `SalesItemEntry` — a channel price only suggests a default `amount` in the Daily Sales entry form, preserving ADR-0039's historical-snapshot principle exactly. Rejected modeling a channel as a `MenuCategory`, which would conflate sales channels with product groupings and duplicate `MenuItem` rows per channel. |
| 0041 | POS Source / Sales Channel Flexibility: Per-Entry, Not a Fixed Mapping | `PosSource` — a fourth Restaurant-scoped master list, structurally identical to `SalesChannel`/`SalesPaymentMethod`/`SalesCategory`. The POS↔channel relationship lives as an optional `posSourceId` (+ `transactionCount`) directly on `SalesChannelEntry`, per day, per line — never a fixed column on `SalesChannel` itself — so one restaurant can run a single POS covering every channel while another splits channels across multiple POS terminals, with no schema change per topology. `DailySalesRecord`'s existing single POS-report header fields are untouched (confirmed with the user); per-POS granularity is answered entirely by new computed `posSourceTotals[]`/`channelsByPosSource[]` aggregation fields, rendered in the UI only when a restaurant actually uses more than one POS source. |
| 0042 | Payment Method POS Source Flexibility, and a Shared Uniqueness Fix | Extends ADR-0041's `posSourceId` pattern to `SalesPaymentMethodEntry`, identically. Also fixes a gap ADR-0041 left in place: both `SalesChannelEntry` and `SalesPaymentMethodEntry`'s unique constraints are widened from `(record, channel/method)` to `(record, channel/method, posSourceId)`, so the same channel or payment method can now genuinely be split across multiple POS terminals on the same business day — the exact overlap ADR-0041's own text implied was already possible but the constraint silently blocked. NULL-safety required switching the service-layer duplicate check from `findUnique` to a `findFirst`-based equality lookup. New `paymentMethodPosSourceTotals[]`/`paymentMethodsByPosSource[]` aggregation fields, kept strictly separate from the channel-side totals — a POS's channel total and its payment-method total are never summed together. |
