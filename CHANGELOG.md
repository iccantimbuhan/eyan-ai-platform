### Added

- **Restaurant Operations Platform — Cash Reconciliation**: Daily/Weekly Sales gain a manager-facing reconciliation of physical cash on hand against a manual discount — `totalSales` is never touched, remaining the source of truth (ADR-0039). Two additive columns: `SalesPaymentMethod.isCashEquivalent` (`Boolean @default(false)`, catalog-level, restaurant-configurable, never inferred from a payment method's name — "Cash Draw," "Bolt Cash," and "Trust/Card Payment" are all just names until a manager explicitly checks the box) identifies which payment methods count as physical cash vs. card/electronic; `DailySalesRecord.actualCashCounted` (`Decimal? @db.Decimal(10,2)`) is the manager's one closing-time cash count per business day, never auto-calculated. The existing `discountsTotal` field is reused as-is for "Manual Discounts Today" rather than adding a new field. A new, separate `CashReconciliationDto` (`physicalCashBasis`, `cardElectronicTotal`, `manualDiscounts`, `expectedCash`, `discrepancy`, `status: BALANCED|SHORT|OVER|NOT_COUNTED`) is computed fresh on every read by one shared `computeCashReconciliation()` function in `daily-sales-record.mapper.ts`, called identically by the single-record mapper and by `SalesAggregationService`'s weekly per-day rollup, so daily and weekly figures can never diverge. `SalesPaymentMethod` gained its first mutable field beyond `name`, requiring a new `PATCH /api/v1/restaurants/:restaurantId/sales-payment-methods/:id` endpoint (the other three reference lists — `SalesChannel`, `SalesCategory`, `PosSource` — stay create/list-only). New `CashReconciliationCard` on the Daily Sales page and a new per-day cash-reconciliation table + weekly summary stats on the Weekly Sales page, both using icon-plus-text status badges (never color alone). A same-sprint architecture-first manual UI review (per the user's explicit "investigate only, do not modify" instruction) caught and fixed a real bug: the new "physical cash" classification checkbox, while present and correctly wired end-to-end, was rendering at the very bottom of an already-long scrollable dialog section, past the entries list and add-entry form — moved to the top of the Payment Methods section, directly under its heading, a placement-only fix with zero logic/data-model change.

  **Amended same sprint — POS-scoped manual discount.** The original formula computed physical cash as one combined sum across every POS source and subtracted the day's entire discount from that single pool. The manager reported this was wrong for a real case: a discount granted against one POS terminal's cash (e.g. POS 1's Trust Pay/Card Payment + Cash Draw) was mathematically bleeding into a different, undiscounted POS terminal's cash (e.g. POS 2's Bolt Cash). Per the user's explicit "do not code yet" instruction, ran an architecture-investigation-only pass first — confirming the exact gap against the live formula and existing tests, and proposing the smallest fix — before touching any file. One additional additive column, `DailySalesRecord.discountPosSourceId` (nullable FK → `PosSource`, `onDelete: SetNull`): `null` means "all POS sources," and reproduces the pre-amendment combined-total formula exactly, for every existing record, with zero backfill — proved mathematically, not merely asserted, since summing gross cash across every POS bucket and then subtracting one flat discount amount is invariant to which bucket "owns" that subtraction for display purposes; only the new `cashByPosSource[]` per-bucket breakdown changes with the scope, the overall total never does. `computeCashReconciliation()` now groups cash entries into per-POS-source buckets (reusing the same `"unassigned"` sentinel-bucket convention `SalesAggregationService` already uses for channel/payment-method POS totals) and applies the discount to exactly the one bucket matching `discountPosSourceId`; every other bucket's expected cash equals its own gross cash, untouched. A discount scoped to a POS source with zero cash entries recorded yet that day still surfaces transparently (gross "0.00," expected cash negative) rather than silently vanishing. `CashReconciliationDto` gained `discountPosSourceId`, `discountPosSourceName`, and `cashByPosSource: { posSourceId, posSourceName, grossCashBasis, discountApplied, expectedCash }[]` — additive only, every prior field keeps its exact name and meaning. `CashReconciliationCard` was redesigned to render "Discountable Physical Cash — POS 1" as a visually distinct section from "Non-Discountable Physical Cash — POS 2" (falling back to a neutral, undifferentiated per-POS layout when no discount scope is set, matching the pre-amendment presentation). `DailySalesDialog` gained a "Discount applies to" select, options sourced dynamically from the restaurant's own `PosSource` catalog — never hardcoded POS names — mapping to `discountPosSourceId` (`null` for the explicit "All POS sources" option). Two additive migrations total this sprint (`isCashEquivalent`/`actualCashCounted`, then `discountPosSourceId`), no backfill, no data rewrite either time.

  36 new backend tests across the base feature and its amendment (physical-cash aggregation across multiple POS sources excluding card/electronic entirely; the exact POS-scoped worked scenario end to end — POS 1 gross/discount/expected trio, POS 2 completely untouched by POS 1's discount; BALANCED/SHORT/OVER/NOT_COUNTED all re-verified with a POS scope set; `discountPosSourceId: null` reproducing the exact legacy combined-total math for the same entries; a POS source with only card/electronic entries never appearing in the cash breakdown; a discount-scoped POS source with zero cash entries still surfacing transparently; cross-restaurant `discountPosSourceId` rejection on both create and update; a payment method's cash classification proven to track `isCashEquivalent` and not its name, in both directions — "Trust/Card Payment" excluded when `false`, included when `true`; weekly aggregation applying the identical POS-scoped rule via the same shared function); full backend suite 1198/1198 passing. 11 new frontend tests, including a dedicated `CashReconciliationCard` regression test built directly from the reported bug's own worked numbers, proving Bolt Cash never visually or numerically shows a discount it didn't receive; full frontend suite 494/494 passing; both typecheck clean; lint clean (0 errors); both production builds succeed. Live-smoke-tested end-to-end against the dev database (real Prisma writes, temporary `PosSource`/`SalesPaymentMethod`/`DailySalesRecord`/`SalesPaymentMethodEntry` rows attached to a real branch, a businessDate far in the future to guarantee no collision with real data) — reproduced the manager's own worked numbers exactly: POS 1 gross €580.65 (€321.00 Trust Pay/Card Payment + €259.65 Cash Draw), discount €61.35, expected €519.30; POS 2 (Bolt Cash) gross and expected both €251.98, discount €0.00, completely unaffected; overall expected cash €771.28; `totalSales` (€1,911.74) confirmed untouched throughout — then fully cleaned up, confirming exact baseline row-count restoration (`posSource: 2, salesPaymentMethod: 14, salesPaymentMethodEntry: 22, dailySalesRecord: 4`, identical before/after) and every real `DailySalesRecord` byte-for-byte unchanged, including one real record that happened to already carry a matching discount amount (€61.35) and actual-cash-counted figure (€324.73) from the manager's own prior manual testing of this exact feature — confirmed its `discountPosSourceId` stayed `null` (the correct legacy-preserving value) and every other field identical before and after. Explicitly not built: Excel export, per-payment-method discounts, per-POS `actualCashCounted`, Slack/WhatsApp/AI ingestion, the future Daily Closing workflow (ADR-0032, proposed/unimplemented).

  **Amended again same sprint — cash/electronic discount split.** The manager reported a second, distinct problem: their POS can't record a discount against the actual amount received at all, so staff enter one combined `discountsTotal` figure covering both a cash-reducing portion and an electronic/card-reducing portion together (e.g. €61.35 total = €49.45 cash + €11.90 electronic), and the formula was subtracting the *entire* combined figure from physical cash, overstating the shortfall by exactly the electronic portion every time — a distinct, orthogonal bug from the POS-scoping amendment above (which controls *which POS bucket* absorbs the discount, not *how much of it* actually reduces cash). Explicitly framed by the user as this one restaurant's specific POS limitation, not a platform-wide accounting rule — the fix stays entirely restaurant-configurable and additive: a restaurant that never touches the new field sees zero behavior change. One more additive, nullable column, `DailySalesRecord.cashDiscountTotal` (`Decimal? @db.Decimal(10,2)`) — `null` means "not configured," reproducing the pre-amendment formula (the full `discountsTotal` reduces cash) byte-for-byte for every existing record, with zero backfill and zero invented allocation for historical rows. `computeCashReconciliation()` now derives `cashReducingDiscount = cashDiscountTotal ?? discountsTotal` and substitutes that (never the raw `discountsTotal`) everywhere the cash-reducing figure was previously used — both the overall `expectedCash` formula and each POS bucket's `discountApplied` — composing unchanged with the existing POS-scoping rule from the first amendment. `electronicDiscountTotal` (`discountsTotal - cashDiscountTotal`) is exposed on `CashReconciliationDto` purely for display, only computed when `cashDiscountTotal` is configured, never itself subtracted from physical cash, never a second stored source of truth. Also found and fixed during inspection (not itself reported by the user, but a real latent bug this amendment's own worked example exposed): `SalesAggregationService`'s weekly `cashReconciliationSummary.totalExpectedCash` was being re-derived from `totalPhysicalCashBasis.minus(discountsTotal)` — a shortcut that happened to be mathematically equivalent before this amendment, but would have silently ignored the electronic-discount portion at the weekly rollup level too; now accumulated from each day's own already-correct `dayCash.expectedCash`, so daily and weekly figures can never diverge on this point. `DailySalesDialog` gained an optional "Cash Discount (optional)" input next to "Manual Discounts Today," with help text explicitly framing it as opt-in and specific to a restaurant whose POS reports one combined discount. `CashReconciliationCard`'s per-bucket discount line was relabeled from "Manual Discounts Today" to "Cash Discount Applied" (since it may now legitimately differ from the full discount figure) and now shows the correct, reduced amount; the Card/Electronic section gained a new "Electronic Discount" line shown next to the relevant payment methods. A cross-field validation (`InvalidCashDiscountError`, 400) rejects a `cashDiscountTotal` greater than `discountsTotal` on both create and update, checked against the record's own effective post-update values so a partial update touching only one of the two fields is still validated correctly. Three additive migrations total across this sprint and both its amendments (`isCashEquivalent`/`actualCashCounted`, then `discountPosSourceId`, then `cashDiscountTotal`), no backfill, no data rewrite at any step. 15 new backend tests (the exact worked example end to end — cash discount reducing cash by exactly its own amount while the electronic portion is never subtracted; `cashDiscountTotal: null` reproducing the pre-amendment formula with no invented allocation; two independently-configured restaurants proven to compute independently from the same code path, neither hardcoded; `cashDiscountTotal` exceeding `discountsTotal` rejected on both create and update; the identical split applied by the weekly rollup via the same shared function); full backend suite 1213/1213 passing. 1 new frontend test (a dedicated `CashReconciliationCard` regression built from this amendment's own worked numbers, proving the electronic-discount portion is shown separately and never reduces the cash-side figures); full frontend suite 495/495 passing; both typecheck clean; lint clean (0 errors, same 21 pre-existing warnings, none new); both production builds succeed. Live-smoke-tested end-to-end against the dev database via the real service layer (temporary, distinctly-named payment-method catalog rows — deliberately never touching the restaurant's real "Cash Draw"/"Trust Pay/Card Payment"/"Bolt Cash" rows, whose `isCashEquivalent` flags the manager has configured for real usage — attached to a real branch, businessDate far in the future) — reproduced the manager's exact worked numbers: physical cash basis €374.18, cash discount applied €49.45 (not the full €61.35), electronic discount €11.90 surfaced separately, POS 1 expected cash €72.75, POS 2 (untouched) expected cash €251.98, overall expected cash €324.73, actual cash counted €324.73, discrepancy €0.00, status BALANCED — all 12 checks passed — then fully cleaned up, confirming exact baseline row-count restoration (`dailySalesRecord: 4, salesPaymentMethod: 14, salesPaymentMethodEntry: 22`, identical before/after). Explicitly not built: a general per-payment-method or multi-way discount allocation engine, auto-derived cash/electronic splits inferred from the payment mix, Excel export, Slack/WhatsApp/AI ingestion, the future Daily Closing workflow (ADR-0032, proposed/unimplemented). Full design rationale: `docs/architecture/decisions/ADR-0043-cash-reconciliation.md` (including both amendment sections).

Per the user's explicit instruction not to write any code before review, ran a full architecture-assessment-only pass first (via plan mode plus a clarifying `AskUserQuestion`), inspecting the current Payment Method/POS Source stack in detail and answering all of the user's specific architecture questions before touching a single file. That inspection surfaced a real, previously-undetected gap: `SalesChannelEntry`'s own unique constraint (`@@unique([dailySalesRecordId, salesChannelId])`, unchanged since Sprint 2C and not addressed by the prior POS Source sprint) actually limited a channel to one entry per day, total, regardless of POS source — the same channel could not yet be split across two POS terminals on the same day either, despite that ADR's own text suggesting it could. The user explicitly confirmed fixing both entry types together in one pass. New nullable `SalesPaymentMethodEntry.posSourceId` column (FK to `PosSource`, `onDelete: SetNull`, mirroring `SalesChannelEntry.posSourceId` exactly); `PosSource` gained a matching `paymentMethodEntries` back-relation. Both `SalesChannelEntry` and `SalesPaymentMethodEntry`'s unique constraints were widened in the same migration from `(record, channel/method)` to `(record, channel/method, posSourceId)` — a strict relaxation, since every row satisfying the old 2-column constraint still satisfies the new 3-column one. (2) **Breakdown percentages** — `ChannelTotalDto.percentOfChannelEntriesTotal` and the equivalent for payment methods/categories are each a share of that breakdown's *own* recorded total, never a share of `totalSales`/`posReportedTotal` (which remain independent, unreconciled figures per ADR-0039 Decision 2) — `null`, not a divide-by-zero error, when the breakdown's own total is zero. (3) **Channel performance** — `activeDays` (days with a recorded entry for that channel) and `averageAmountPerActiveDay` per channel; the new `ChannelPerformanceSection` labels the top channel by amount and by average/day with deliberately neutral badges ("Highest recorded sales" / "Highest average sales/day"), never "best channel," since gross sales alone doesn't establish profitability across platforms with different commissions or pricing. (4) **Reconciliation** — `totalSales` vs. `posReportedTotal` vs. `channelEntriesTotal` and their variances, surfaced on both the weekly summary and — new this sprint — the single-day response via a `reconciliation` field added to `DailySalesRecordResponseDto` (computed in the mapper using real `Prisma.Decimal` arithmetic). A non-zero variance is never auto-corrected and never labeled an error; the new `ReconciliationCard` shows a neutral "Requires review" badge plus an explicit note that independent figures aren't automatically reconciled. ### Fixed

- **Public pages no longer wait on authentication (Phase 2C)**: the public landing page (and every other route outside `/app/*`) previously rendered behind a global `AuthProvider` gate wrapping the entire router — meaning a stale-but-present 7-day session cookie could show a full-screen "Restoring session..." wait, or even hard-redirect a first-time visitor to `/sign-in`, before the homepage ever appeared. `AuthProvider` is now scoped to `/app/_authenticated` only (moved into `AuthenticatedLayout`); the public landing page, sign-in, and error pages render immediately with zero auth dependency, while protected routes restore the session exactly as before. Both are fixed; the hard `window.location.href` redirect was also replaced with an SPA `router.navigate()` (via a small new `lib/router-instance.ts` holder, avoiding a circular import). - **Hugging Face image provider** (Sprint 4.4): a third real `ImageProvider` — `HuggingFaceProvider`, using Hugging Face's official Inference Providers API (`hf-inference`, Hugging Face's own first-party serverless infrastructure). No specific model is assumed available; `HUGGINGFACE_MODEL` selects any text-to-image model served through `hf-inference` (defaults to `black-forest-labs/FLUX.1-schnell`). Selectable per-request (`provider: "huggingface"`) or as the platform default (`IMAGE_PROVIDER=huggingface`, requiring `HUGGINGFACE_API_KEY`, validated fail-fast at startup; `HUGGINGFACE_BASE_URL`/`HUGGINGFACE_TIMEOUT` configurable). Its startup health check validates authentication and model access via free Hugging Face Hub metadata lookups, without generating an image or incurring any cost. See `docs/HUGGINGFACE_PROVIDER.md` and `docs/HUGGINGFACE_SETUP.md`. Not yet the default in production; still opt-in.
- **Image Studio frontend** (Sprint 4.3, extended Sprint 4.4): the first frontend surface for AI-generated images — a minimal "Images" tab inside each Content Studio project's workspace, alongside the existing text-content generation tab. Lets you pick a provider (server default / Gemini / ComfyUI / Hugging Face / Fake, remembered across visits), enter a prompt, and view the generated image with a provider badge, a provider-specific loading hint, and a provider-prefixed error message. Not a full gallery — no history list, delete, regenerate, or download yet.
- **Asset Library & QA workflow** (Sprint 5): two new tabs in every project's workspace — **Assets** (every generated content item, image, and project-scoped prompt template in one searchable, filterable, batch-actionable card grid: `GET /api/v1/assets`, `GET/PATCH/DELETE /api/v1/assets/:assetType/:sourceId`, `POST .../regenerate`, `POST .../duplicate`, `GET .../versions`, `POST /api/v1/assets/batch`) and **Review** (a per-project queue filtered by QA status with inline Approve/Reject/Add Notes). Every asset has a QA review lifecycle (Draft → Needs Review → Approved → Rejected → Published) with a reusable Pass/Fail/Comment checklist (separate item sets for content vs. images), reviewer notes, and a QA score — all additive (`AssetReview`, new table) with zero changes to how `GeneratedContent`/`GeneratedImage` are generated. Regenerating an asset creates a new, linked version (`AssetVersion`, new table) with Version History and a side-by-side Compare view; Duplicate creates an independent copy with no version link. Prompt templates can now be scoped to a project (`SavedPrompt.projectId`, nullable — existing global prompts in the Prompt Library page are unaffected) via a "New Prompt Template" action in the Asset Library, making them real, reviewable assets. Downloads/exports (Markdown, JSON, and image files) are entirely client-side — no new export endpoints. Full design rationale: `docs/ASSET_LIBRARY.md` and `docs/architecture/decisions/ADR-0008-asset-library-polymorphic-review-versioning.md`.

### Security

- **Third-party credentials are now encrypted at rest** (Sprint 7.1): `AutomationConnection` — the new credential store behind the MCP Foundation — encrypts every stored credential with AES-256-GCM before it is ever written to the database, a stricter posture than the plain-`.env`-only pattern used for the platform's own provider keys, since these credentials are authorized on behalf of individual users rather than the platform operator. Decryption happens in exactly one place (`CredentialManagerService`); no API response ever returns a raw credential value, and there is deliberately no `/reveal` endpoint anywhere in the new API surface.
- **AI Image Studio no longer forwards raw internal error detail to API responses** (Sprint 4.2 Phase 0): a failed image generation previously returned the underlying provider/storage error message verbatim to the client, which could include vendor-internal detail (hostnames, library-specific text). The API response is now always a fixed, safe message; the full detail is still recorded and visible to the image's own owner via `GET /images/:id`.
- **Per-user data ownership enforced on Content Studio projects and generated content** (Sprint 3.5): previously, any authenticated user could read, list, or delete any other user's project or generated content by ID. `POST /projects`, `GET /projects`, `GET /projects/:id`, `DELETE /projects/:id`, `GET /content`, `GET /content/:id`, and `DELETE /content/:id` now all scope to the requesting user; a project or content item that exists but belongs to someone else returns `404` (not `403`), consistent with how this ownership pattern already worked for Saved Prompts.

### Changed

- **AI Image Studio hardening** (Sprint 4.2 Phase 0): image generation failures now report a specific, safe error message depending on what actually failed (the provider vs. storage vs. a database write), instead of one generic error either way — and the raw underlying failure detail is no longer forwarded to the API response (it's still visible to the image's own owner via `GET /images/:id`). `provider` and `negativePrompt` request fields are validated more strictly (trimmed, and `provider` restricted to a safe charset) — no existing valid request is affected. The backend now fails to start, with a clear error, if its configured local image-storage directory isn't writable, instead of only discovering that on the first real generation attempt.
- AI provider default model corrected from an unavailable `qwen2.5-coder:14b` to the installed `qwen2.5-coder:7b`.
- Maximum generated tokens is now configurable via `OLLAMA_MAX_TOKENS` (default 500) instead of unbounded.
- AI provider requests now use a request timeout instead of hanging indefinitely on a stuck generation — raised from 180s to 300s after production traffic showed a cold model load (the first request after a deploy or restart) can exceed 180s on our current hardware.
- Generation History entries longer than a preview length now collapse behind a "Read more" toggle instead of always showing the full response, so the history stays easy to browse as it grows.
- The deployment script (`deploy.sh`) now automatically warms the configured Ollama model right after the post-deploy health check passes, so the first real user request after a deploy never hits a cold model load. Fails the deploy with a clear error if the warm-up itself fails.
- The production reverse proxy's `/api/` route now allows up to 330s for a response (previously nginx's unconfigured 60s default), matching the backend's own AI provider timeout with a safety margin, so long-running generations no longer receive a false `504 Gateway Time-out` from nginx while the backend is still working.

### Fixed

- **Hugging Face image generation was failing with `410 "deprecated and no longer supported by provider hf-inference"`**: Hugging Face narrowed the `hf-inference` provider's catalog and dropped the configured default model (`black-forest-labs/FLUX.1-schnell`) from it entirely — a provider-side change, not a bug, but one the original hand-rolled REST client (fixed to `hf-inference` specifically) couldn't route around. `HuggingFaceProvider` now generates through Hugging Face's own official `@huggingface/inference` SDK with a new `HUGGINGFACE_PROVIDER` setting (default `"auto"`), letting Hugging Face's router pick whichever Inference Providers partner currently serves the configured model, with automatic failover if that changes again. `HUGGINGFACE_BASE_URL` is no longer used (harmlessly ignored if still set). See [docs/HUGGINGFACE_PROVIDER.md](docs/HUGGINGFACE_PROVIDER.md#provider-migration) for the full incident and migration notes.
- **Generated images were never actually loadable over HTTP** (discovered and fixed in Sprint 4.3): `LocalDiskStorageProvider` and the database have tracked a public URL path for every generated image since Sprint 4.1, but nothing ever served it — Express had no static route for it. The backend now serves it directly; production's nginx still needs a manual, one-line proxy addition to finish the fix there (see `docs/COMFYUI_SETUP.md`).
- `POST /chat` was failing on every call in production due to a misconfigured, non-existent model — now works correctly.
- Reselecting the currently-selected template in the content generation form no longer clears the values you'd already typed into its fields.
- Content generation on a project page no longer reports "Generation Failed" for responses that take longer than 30 seconds to produce — the generate request now waits as long as the backend does, instead of the app-wide default timeout cutting it off early while the backend keeps working and saves the content anyway.
- The project workspace page (generate content, view output, browse history) now uses the same page layout, width, and header as the rest of the app, instead of rendering full-width with no page header.
- Deleting a generated content entry from Generation History now asks for confirmation first, instead of deleting immediately on click.
- **Production incident**: content generation on longer prompts intermittently failed with a `503` from the backend or a `504` from nginx, even though generation actually succeeded and saved — caused by a chain of three independently-configured timeouts (frontend, backend AI provider, and an unconfigured nginx default) that were never reconciled against real generation time or against each other. All three are now aligned; see `tasks/completed/sprint-3-prompt-library.md` for the full incident record.
