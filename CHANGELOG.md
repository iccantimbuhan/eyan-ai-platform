### Fixed

- **Restaurant Operations sidebar hidden after Sprint 0's initial deploy**: `prisma migrate deploy` created the new tenancy tables, but `deploy.sh` had never had a seed step — the `restaurant` `Permission` row and every tenancy data row simply didn't exist in production, so both the RBAC gate and the Module Registry gate on the sidebar item correctly evaluated to hidden. Root-caused via read-only DB inspection (no code changes needed to diagnose it). Fixed by splitting seeding into two tiers: `backend/prisma/bootstrap.ts` (new — roles, permissions, Restaurant tenancy foundation; idempotent, now run automatically by `deploy.sh` right after migrations) versus `backend/prisma/seed.ts` (unchanged role — demo/sample content, e.g. the portfolio demo account; stays a deliberate manual step, permanently, since running it unconditionally against a future real commercial tenant's database would be wrong). The original implementation's placeholder manager account is removed; `OrganizationMember` is now granted to whichever real users already hold the platform's global `Owner` role. Ran once against production directly and verified read-only: `Permission` count went from 31 to exactly 32 (the one new `restaurant` row), every existing table's row count unchanged. Full design rationale: `docs/architecture/decisions/ADR-0035-deployment-bootstrap-strategy.md`.

- **Production Stabilization — AI Sales Qualification Pipeline (Sprint 5.2)**: every real qualification whose model output included `buyingIntent: "UNKNOWN"` (a legitimate low-confidence answer, not malformed output) was silently breaking the entire automation chain — the CRM write-back validator only accepted `LOW/MEDIUM/HIGH`, so it 400'd, n8n reported "Bad request - please check your parameters," and the lead stayed stuck at `VALIDATED` forever. `buyingIntent`/`urgency`/`riskLevel` now accept `"UNKNOWN"` at the validator boundary and normalize to `null` before the Prisma write (the DB enum still only has three real values — no migration). Separately, and only discovered while live-validating the fix: Workflow 4's Slack/Email notification steps referenced `$json` for lead/qualification data, but on the real assignment path `$json` had already been overwritten by the `Assign Salesperson` HTTP call's own response by the time Slack's node ran — so real notifications had likely never worked once a lead actually got assigned, only in isolated tests that skipped assignment. Fixed by referencing `$('Verify & Parse').item.json` explicitly, the same pattern Workflow 3 already established. Also fixed, found along the way: Express's `trust proxy` was never set despite running behind nginx (the source of the separately-reported `ERR_ERL_UNEXPECTED_X_FORWARDED_FOR` warning — confirmed unrelated to the pipeline failure, fixed anyway since it's a real, one-line correctness gap). Root-caused entirely from n8n's own execution history (no new logging needed) and verified live four times, including a real headless-browser submission through `https://eyan.fyi/contact` with a user-confirmed Slack delivery. Full report: `tasks/completed/sprint-5-2-production-stabilization.md`.

- **AI Core Foundation — Phase 1**: a new platform module — MCP Foundation's architectural sibling — that gives every business module a shared, provider-agnostic way to call AI, generalizing the registry pattern already proven for images (`ImageProviderFactory`) to text/chat generation for the first time (deliberately superseding ADR-0001, "Single AI Provider, No Gateway," for that specific case). Business modules and future n8n workflows invoke an **AI Capability** by key (e.g. `lead-qualification`) — never a Brain, Provider, Model, or Prompt directly; each Capability resolves to exactly one **AI Brain**, a reusable configuration (provider, model, prompt, routing policy). `AiRoutingService` resolves and caches that chain in-process, runs a corrective-retry loop and a configured per-Brain fallback, and classifies every outcome (valid / schema-invalid / transient / definitive failure) the same way `eyan-automation-hub`'s existing Workflow 3 already does — never stranding a caller. Four provider plugins ship: Ollama (a direct generalization of the existing, already-verified `OllamaProvider`) plus new OpenAI, Anthropic, and Gemini plugins (thin REST translations, no new SDK dependency). A new **AI Playground** (`/app/ai-core/playground`) lets you execute a Capability or Brain with one-off provider/model/prompt overrides — fully isolated from production usage/cost reporting via a domain tag on the same usage-log table, never a parallel logging system. New `/app/ai-core/*` pages (Dashboard, Capabilities, Brains, Providers, Models, Playground, Usage, Costs, Health, Audit Logs) under a new sidebar group, gated by new `aicore`/`aicoreadmin` permissions. This phase reached implementation only after a full Phase 0 (Technical Design Document) → Phase 0.5 (Architecture Review, which required six real fixes before approval) → Architecture Freeze process — see `docs/architecture/decisions/ADR-0021-ai-core-foundation.md`. **Nothing existing changed**: `ChatService`, `ContentService`, the AI Video Editing Pipeline, and `eyan-automation-hub`'s Workflow 3 all continue to work exactly as before — migrating them onto AI Core is explicitly future, separately-approved work. Full design rationale: `docs/architecture/decisions/ADR-0021-ai-core-foundation.md`.

### Fixed

- **Public pages no longer wait on authentication (Phase 2C)**: the public landing page (and every other route outside `/app/*`) previously rendered behind a global `AuthProvider` gate wrapping the entire router — meaning a stale-but-present 7-day session cookie could show a full-screen "Restoring session..." wait, or even hard-redirect a first-time visitor to `/sign-in`, before the homepage ever appeared. `AuthProvider` is now scoped to `/app/_authenticated` only (moved into `AuthenticatedLayout`); the public landing page, sign-in, and error pages render immediately with zero auth dependency, while protected routes restore the session exactly as before. Browser verification of this fix also surfaced two real bugs in the token-refresh interceptor: (1) a circular deadlock — a doubly-invalid (access + refresh) token caused the app to hang forever on "Restoring session..." rather than ever redirecting, because the refresh call's own 401 recursively re-entered the same retry logic and awaited its own in-flight promise; (2) concurrent 401s could each independently redirect to `/sign-in`, nesting the `redirect` search param inside itself. Both are fixed; the hard `window.location.href` redirect was also replaced with an SPA `router.navigate()` (via a small new `lib/router-instance.ts` holder, avoiding a circular import). The Presentation Engine, RBAC, and the "Watch Presentation" demo-login flow are all unchanged and were re-verified end-to-end. Full design rationale: `docs/architecture/decisions/ADR-0017-auth-provider-scoping.md`.

- **Finance Management — Dashboard & Expenses** (Sprint A): a new Finance Management area for household expense/budget tracking, reached from a new "Finance Management" sidebar section (Admin-only, gated by a new `finance` permission). The **Dashboard** (`GET /api/v1/finance/dashboard`) shows your monthly budget, total expenses, remaining budget, a 6-month spending-trend chart, a spending-by-category chart, and your most recent expenses. **Expenses** (`GET/POST /api/v1/finance/expenses`, `GET/PATCH/DELETE /api/v1/finance/expenses/:id`) is a full CRUD table with search, category filtering, and sorting; adding an expense only requires an amount and a category — everything else (date, payment method, notes, "repeat monthly") is optional, so logging a purchase takes well under 30 seconds. Checking "Repeat monthly" on an expense automatically logs it again every month going forward, computed on the fly (no background scheduler) so a household that hasn't opened the app in a while still gets every missed month backfilled correctly the next time it does. Monthly budgets (`GET/PUT /api/v1/finance/budget`) carry forward automatically from the previous month if you haven't set a new one yet. Money amounts are stored and computed with exact decimal precision throughout — never floating-point JavaScript math. Bills, Savings, Reports, and receipt uploads are planned for later sprints. Full design rationale: `docs/architecture/decisions/ADR-0013-finance-management-foundation.md`.

- **AI Video Editing Pipeline — AI Transcription & Subtitle Generation** (Sprint 7.2.4): the `subtitles` operation — plannable since Sprint 7.2.2, rejected as not-yet-executable since Sprint 7.2.3 — now actually runs. Executing a workflow plan containing a `subtitles` step extracts the audio, transcribes it with a real, self-hosted speech-to-text model (Faster Whisper, CPU-only, configurable model size via `WHISPER_MODEL`), generates a standard `.srt` subtitle file, and burns it into the video with FFmpeg — producing a real edited video with visible, permanently-overlaid captions. The generated subtitle file is saved alongside the edited video, and the execution response now includes it. The "Execute a Workflow" panel shows whether subtitles were generated, with a plain, read-only link to preview the `.srt` file — no subtitle editor, timeline, or styling controls yet. - **AI Video Editing Pipeline — Execution Engine + Core FFmpeg Operations** (Sprint 7.2.3): you can now actually execute a previously generated editing plan (`POST /api/v1/video-edit/execute`) — the five most common operations (`trim`, `remove_silence`, `normalize_audio`, `resize`, `brightness`) run for real via FFmpeg, sequentially, and the result is saved as a new, real edited video you can preview, review, and find in the Asset Library right alongside the original. ### Security

- **Third-party credentials are now encrypted at rest** (Sprint 7.1): `AutomationConnection` — the new credential store behind the MCP Foundation — encrypts every stored credential with AES-256-GCM before it is ever written to the database, a stricter posture than the plain-`.env`-only pattern used for the platform's own provider keys, since these credentials are authorized on behalf of individual users rather than the platform operator. Decryption happens in exactly one place (`CredentialManagerService`); no API response ever returns a raw credential value, and there is deliberately no `/reveal` endpoint anywhere in the new API surface.
- **AI Image Studio no longer forwards raw internal error detail to API responses** (Sprint 4.2 Phase 0): a failed image generation previously returned the underlying provider/storage error message verbatim to the client, which could include vendor-internal detail (hostnames, library-specific text). The API response is now always a fixed, safe message; the full detail is still recorded and visible to the image's own owner via `GET /images/:id`.
- **Per-user data ownership enforced on Content Studio projects and generated content** (Sprint 3.5): previously, any authenticated user could read, list, or delete any other user's project or generated content by ID. `POST /projects`, `GET /projects`, `GET /projects/:id`, `DELETE /projects/:id`, `GET /content`, `GET /content/:id`, and `DELETE /content/:id` now all scope to the requesting user; a project or content item that exists but belongs to someone else returns `404` (not `403`), consistent with how this ownership pattern already worked for Saved Prompts.

### Changed

- **AI Image Studio hardening** (Sprint 4.2 Phase 0): image generation failures now report a specific, safe error message depending on what actually failed (the provider vs. storage vs. a database write), instead of one generic error either way — and the raw underlying failure detail is no longer forwarded to the API response (it's still visible to the image's own owner via `GET /images/:id`). `provider` and `negativePrompt` request fields are validated more strictly (trimmed, and `provider` restricted to a safe charset) — no existing valid request is affected. The backend now fails to start, with a clear error, if its configured local image-storage directory isn't writable, instead of only discovering that on the first real generation attempt.
- AI provider default model corrected from an unavailable `qwen2.5-coder:14b` to the installed `qwen2.5-coder:7b`.
- Maximum generated tokens is now configurable via `OLLAMA_MAX_TOKENS` (default 500) instead of unbounded.
- AI provider requests now use a request timeout instead of hanging indefinitely on a stuck generation — raised from 180s to 300s after production traffic showed a cold model load (the first request after a deploy or restart) can exceed 180s on our current hardware.
- Generation History entries longer than a preview length now collapse behind a "Read more" toggle instead of always showing the full response, so the history stays easy to browse as it grows.
- The deployment script (`deploy.sh`) now automatically warms the configured Ollama model right after the post-deploy health check passes, so the first real user request after a deploy never hits a cold model load. Fails the deploy with a clear error if the warm-up itself fails.
- The production reverse proxy's `/api/` route now allows up to 330s for a response (previously nginx's unconfigured 60s default), matching the backend's own AI provider timeout with a safety margin, so long-running generations no longer receive a false `504 Gateway Time-out` from nginx while the backend is still working.

### Fixed

- **Hugging Face image generation was failing with `410 "deprecated and no longer supported by provider hf-inference"`**: Hugging Face narrowed the `hf-inference` provider's catalog and dropped the configured default model (`black-forest-labs/FLUX.1-schnell`) from it entirely — a provider-side change, not a bug, but one the original hand-rolled REST client (fixed to `hf-inference` specifically) couldn't route around. `HuggingFaceProvider` now generates through Hugging Face's own official `@huggingface/inference` SDK with a new `HUGGINGFACE_PROVIDER` setting (default `"auto"`), letting Hugging Face's router pick whichever Inference Providers partner currently serves the configured model, with automatic failover if that changes again. `HUGGINGFACE_BASE_URL` is no longer used (harmlessly ignored if still set). See [docs/HUGGINGFACE_PROVIDER.md](docs/HUGGINGFACE_PROVIDER.md#provider-migration) for the full incident and migration notes.
- **Generated images were never actually loadable over HTTP** (discovered and fixed in Sprint 4.3): `LocalDiskStorageProvider` and the database have tracked a public URL path for every generated image since Sprint 4.1, but nothing ever served it — Express had no static route for it. The backend now serves it directly; production's nginx still needs a manual, one-line proxy addition to finish the fix there (see `docs/COMFYUI_SETUP.md`).
- `POST /chat` was failing on every call in production due to a misconfigured, non-existent model — now works correctly.
- Reselecting the currently-selected template in the content generation form no longer clears the values you'd already typed into its fields.
- Content generation on a project page no longer reports "Generation Failed" for responses that take longer than 30 seconds to produce — the generate request now waits as long as the backend does, instead of the app-wide default timeout cutting it off early while the backend keeps working and saves the content anyway.
- The project workspace page (generate content, view output, browse history) now uses the same page layout, width, and header as the rest of the app, instead of rendering full-width with no page header.
- Deleting a generated content entry from Generation History now asks for confirmation first, instead of deleting immediately on click.
- **Production incident**: content generation on longer prompts intermittently failed with a `503` from the backend or a `504` from nginx, even though generation actually succeeded and saved — caused by a chain of three independently-configured timeouts (frontend, backend AI provider, and an unconfigured nginx default) that were never reconciled against real generation time or against each other. All three are now aligned; see `tasks/completed/sprint-3-prompt-library.md` for the full incident record.
