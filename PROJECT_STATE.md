## Current Sprint

**Restaurant Operations Platform — Payment Method POS Source Flexibility — COMPLETE.** Extends the prior sprint's `posSourceId` pattern from `SalesChannelEntry` to `SalesPaymentMethodEntry`, so a restaurant reporting different payment methods per POS terminal (e.g. POS 1: Cash/Card/Wolt, POS 2: Wolt/Bolt) can represent it — including the same payment method appearing under more than one POS on the same business day. Per the user's explicit "DO NOT CODE YET" instruction, ran a full architecture-assessment phase first (via plan mode + `AskUserQuestion`), inspecting the current Payment Method/POS Source stack and answering all 15 of the user's specific questions before any file was touched. That inspection surfaced a real, pre-existing gap not previously caught: `SalesChannelEntry`'s own unique constraint (`@@unique([dailySalesRecordId, salesChannelId])`, unchanged since Sprint 2C, not touched by the prior POS Source sprint) actually limited a channel to one entry per day, total — the same channel could not yet be split across two POS terminals on the same day either, contradicting that ADR's own text. The user confirmed (via `AskUserQuestion`) fixing both entry types together. Both `SalesChannelEntry` and `SalesPaymentMethodEntry`'s unique constraints were widened in one migration from `(record, channel/method)` to `(record, channel/method, posSourceId)`; because Postgres treats `NULL` as distinct from every other `NULL` in a unique index, the service-layer duplicate pre-check moved from `findUnique` on the compound key to a `findFirst`-based plain equality lookup, which correctly catches a duplicate no-POS entry too. New `paymentMethodPosSourceTotals[]`/`paymentMethodsByPosSource[]` aggregation fields mirror the channel-side ones exactly but are kept structurally separate — a POS's channel total is never summed with its payment-method total, preserving ADR-0039's channel-vs-payment-method independence principle. `PaymentMethodEntrySection` gained the identical POS Source select `ChannelEntrySection` already had (reusing the same hooks); `PosSourcePerformanceSection` gained an independently-gated Payment Methods block — a restaurant using POS sources for one dimension but not the other sees exactly the sections that apply. See ADR-0042.

**Also complete — Restaurant Operations Platform POS Source / Sales Channel Flexibility.** Real restaurants run different POS/channel topologies — a single POS covering every channel, multiple POS terminals each covering a different subset of channels, or a single POS/single-channel setup — and the relationship can change over time, so it must never be hardcoded (no "POS 1 = MyPOS" assumption anywhere). Investigated the existing Sales Foundation first: `SalesChannel` was already Restaurant-scoped and configurable; `SalesChannelEntry` had only `amount`, no transaction count and no POS-source reference; POS report metadata lived as a single set of fields directly on `DailySalesRecord`, implicitly assuming one POS report per branch per day. New `PosSource` — a fourth Restaurant-scoped master list, identical shape to `SalesChannel`/`SalesPaymentMethod`/`SalesCategory` — is deliberately never linked to `SalesChannel` at the master-list level (that would hardcode a fixed mapping); instead an optional `posSourceId` (+ `transactionCount`, mirroring the existing `SalesPaymentMethodEntry` field) was added directly to `SalesChannelEntry`, so the POS↔channel relationship is a per-day, per-entry fact. Confirmed with the user (via `AskUserQuestion`) that `DailySalesRecord`'s existing single POS-report header fields stay untouched — no new `SalesPosReport` child table this sprint; per-POS reporting granularity is answered entirely by two new computed aggregation fields, `posSourceTotals[]` (with an explicit, never-dropped "unassigned" bucket for untagged entries) and `channelsByPosSource[]` (answers "sales by POS + channel combination"). A new `PosSourcePerformanceSection` on the Weekly Sales page renders only when a restaurant actually tags a channel entry with a real POS source — every restaurant on the platform today (single-POS) sees zero UI change. One additive migration: 1 new table, 2 new nullable columns on `SalesChannelEntry`. See ADR-0041.
