## Status

**Sprint 4.3 — ComfyUI Image Provider (2026-07-24):** Added `ComfyUIProvider`, a self-hosted `ImageProvider` talking to ComfyUI's standard REST API (`POST /prompt` → poll `GET /history/{id}` → `GET /view`), registered alongside `fake`/`gemini` with zero changes to `ImageService`, routes, or validators — same non-negotiable as Gemini's own integration. Generation parameters are injected into user-authored JSON workflow templates (`backend/resources/workflows/*.json`) via `{{PLACEHOLDER}}` substitution (`workflow.loader.ts` + `workflow.mapper.ts`), so new ComfyUI workflows never require backend code changes; no ComfyUI node id is ever hardcoded — the result image is found by scanning `/history`'s output nodes for the first one with an image, not by assuming a specific node. Like `GeminiImageProvider`, it never sanitizes its own errors, preserving Phase 0's raw-detail-to-owner / safe-message-to-client separation. Config (`COMFYUI_URL`/`COMFYUI_WORKFLOW`/`COMFYUI_TIMEOUT`/`COMFYUI_POLL_INTERVAL`) is fail-fast validated at boot (synchronous, network-free, matching this codebase's existing pattern); a separate, non-fatal `logComfyUIHealthCheck()` also runs at boot to report live reachability without blocking startup on a network call. Shipped alongside: a minimal "Images" tab in Content Studio's existing project workspace (provider selector persisted to localStorage, prompt input, generated-image display with a provider badge, sanitized server error messages surfaced directly since Phase 0 already guarantees they're safe to show) — the negotiated-down scope of the sprint's original "integrate into the existing image generation UI" ask, since no such UI existed yet. Discovered mid-sprint and fixed: generated images were never actually servable over HTTP (see Current Sprint above). 219/219 tests passing (43 backend + 12 frontend, all new), typecheck/lint/build clean on both sides, fully live-validated (fake-provider generation + the new static file serving + comfyui's graceful, sanitized failure against an intentionally-unreachable ComfyUI instance) against a throwaway backend instance — production untouched throughout. Full detail in the sprint log.

**Sprint 4.2, Phase 1 — Gemini Image Provider Integration (2026-07-24):** Added `GeminiImageProvider`, using Google's official `@google/genai` SDK, as the first real `ImageProvider` implementation — plugging into the registry Sprint 4.1 built with zero changes to `ImageService`, routes, controllers, or validators. It deliberately does not sanitize its own errors, letting them propagate to `ImageService`'s existing Phase 0 stage-based handling, so the raw-detail-preservation work that phase did isn't silently undone by the first real provider. Maps requested width/height to the nearest of Gemini's supported aspect ratios (arbitrary pixel dimensions aren't supported); ignores `negativePrompt` (no native equivalent) rather than inventing a prompt-engineering workaround; always reports output format as `png` (the only format Gemini produces), which surfaced — but didn't cause — a pre-existing gap where `ImageService` never reconciles a provider's actual output format against the format it persisted before generation (flagged as a follow-up, not fixed here, since fixing it means touching `ImageService`). `validateGeminiProviderConfig()` fails the process at boot if `IMAGE_PROVIDER=gemini` but `GEMINI_API_KEY` is unset, verified live (immediate crash, exit 1, before any server binds). 125/125 tests passing (17 new, `@google/genai` fully mocked — no real network calls in the suite), typecheck and build clean. No real, billed Gemini API call has been made in production or otherwise — treated the first real call as worth asking about first, not assuming. Full detail in the sprint log.

**Sprint 4.2, Phase 0 — Production Readiness (2026-07-24):** Hardened the Sprint 4.1 pipeline without changing its architecture, framed explicitly around this project's purpose as an AI Content Production / Content Moderation portfolio. `validateLocalDiskStorageConfig()` now fails the process at boot if the storage root isn't writable, mirroring the existing provider-config fail-fast check. `ImageService.generate()`'s error handling now attributes failures to a specific stage (initial record creation, provider call, storage call, final status update) instead of one generic catch-all, and — the most consequential fix — no longer forwards raw underlying error text (which could include vendor/internal detail) to the HTTP client; a fixed, safe message is thrown instead, while the full detail is still persisted to the owner-visible `errorMessage` column. Every lifecycle event (generation start, provider success/failure, storage success/failure, completion, deletion, provider resolution) now has a corresponding log line. All of it verified live against a throwaway instance, not just asserted in tests: an unwritable storage root crashes the process at boot with a clear message, and real log output was inspected directly to confirm the expected sequence fires. 108/108 tests passing (10 new), typecheck and build clean. Full detail in the sprint log.

**Sprint 4.1 — AI Image Studio, Backend Pipeline (2026-07-24):** Five independently-reviewed phases built a complete internal image-generation pipeline before any real, billable AI provider was integrated. `GeneratedImage` hangs off `ContentProject` with ownership derived transitively (no duplicate `userId` column, extending ADR-0007). `ImageProvider` and `StorageProvider` are independent abstractions — a provider only ever produces bytes, storage only ever persists bytes it's handed, `ImageService` is the sole orchestrator. The full request → generate → store → persist → retrieve → delete cycle was proven correct using a deterministic, in-process `FakeImageProvider` — including failure paths (provider failure, storage failure, a DB-layer failure occurring *after* a successful generation, which a Phase 5 fix stopped from being mislabeled as a failed generation) — validated with real HTTP requests against a throwaway instance on a separate port, production never touched. 98/98 tests passing (46 new this sprint), typecheck and build clean throughout. Full detail in the sprint log.

Every fix in this chain was validated with a real, live request against production (not just log inspection or configuration review) before being considered resolved — full timeline, root-cause chain, and evidence in `tasks/completed/sprint-3-prompt-library.md`.

## Open Risks / Known Issues

- **Production nginx doesn't yet proxy `/uploads/` to the backend** — Express now correctly serves generated images (fixed this sprint), but nginx's `eyan.fyi` site config only proxies `/api/`, so a generated image's URL would still 404 in production until a one-line `location /uploads/ { proxy_pass ...; }` block is added manually (sudo-gated, outside version control — see `docs/COMFYUI_SETUP.md#5-production-serving-generated-images` for the exact snippet). Local dev is unaffected.
- **Sprint 4.1's, Sprint 4.2's, and Sprint 4.3's application code is all undeployed** while Sprint 4.1's migrations are already live — recommend deploying (and adding the nginx block above) before any further Sprint 4 work begins, so nothing builds on an untested deploy of three sprints' worth of undeployed code.
- **No real Gemini API call has ever been made**, and **no real ComfyUI instance has ever been exercised against this integration** — both providers' behavior is verified via mocked tests plus boot-only/network-reachability live checks, never an actual paid or self-hosted generation. `GEMINI_API_KEY` already exists in production `.env` (apparently pre-provisioned); no ComfyUI instance has been stood up anywhere yet. `IMAGE_PROVIDER` is still `fake` in production. Recommend a small, explicit, approved real-provider smoke test for each before either is used for anything user-facing.
- **Known metadata gap, exposed by Gemini, not fixed**: `ImageService.generate()` persists the requested `format` before generation and never reconciles it against what a provider actually returned. `GeminiImageProvider` always produces PNG regardless of what was requested, so a `jpg`/`webp` request against Gemini will store a DB row whose `format` doesn't match the actual file on disk. `ComfyUIProvider` derives format from the actual output filename (not affected the same way), but the underlying gap in `ImageService` is unchanged. Not fixed, since fixing it means touching `ImageService`, out of scope for both phases that exposed it.
- No rate limiting or per-user/per-project generation caps exist for image generation. Still harmless today (no real call has been made yet on any provider), but a hard prerequisite before any real, billable/resource-intensive provider goes live in production — flagged again here so it isn't lost.
- No retention/cleanup policy for orphaned local-disk files (e.g. a crash between a successful storage write and the following DB write). Narrow window, not yet hardened against.
- **Image Studio's frontend is a minimal single-generation slice, not a full feature** — no gallery/history list, no delete UI, no regenerate/download. It reuses `GeneratedImageItem` shaped exactly like the backend's `ImageResponseDto`, and `resolveImageUrl()` hardcodes the same `/uploads/images` path convention as the backend's `STORAGE_PUBLIC_BASE_URL` default — the two aren't otherwise linked, so changing one without the other would silently break image loading.
- ComfyUI-specific: no per-request seed/cfg/steps override (fixed defaults + random seed only); no per-request workflow selection (one server-wide `COMFYUI_WORKFLOW`); the two example workflow templates (`sdxl.json`, `flux.json`) reference specific model filenames that must exist in whichever ComfyUI installation is actually used — see `docs/COMFYUI_SETUP.md`.
- Frontend lint: 26 pre-existing errors, 3 pre-existing warnings, repo-wide (`chat.service.ts`, `use-login.ts`, `user-auth-form.tsx`, `use-projects.ts`, `model-card.tsx`, `stat-card.tsx`, `useHealth.ts`, `useModels.ts`, `useModelsList.ts`, `main.tsx`, `auth-provider.tsx`, `api.ts`, plus two React Compiler table-memoization warnings). None are in Content Studio's own files, including this sprint's new ones.
- 2 pre-existing frontend test failures in `search-provider.test.tsx` (command palette navigation, timeout-based) in addition to the 2 long-standing `user-auth-form.test.tsx` failures — both confirmed pre-existing, neither caused by this project's Content Studio work.
- No CI/CD auto-deploy exists yet (a standing risk since Sprint 1.1) — `deploy.sh` is manually triggered and requires sudo privileges this session does not have.
- Minor, deliberately out-of-scope items from the Content Studio UI investigation: `ProjectCard.tsx`/`QuickActions.tsx`/`ContentPipeline.tsx` use double-quoted `className` strings against the repo's `singleQuote: true` Prettier rule; `QuickActions` and `ContentPipeline` on the Content Studio dashboard render static, non-functional placeholder data that looks real; content-studio query keys are inconsistently constructed (inline arrays vs. one shared exported constant); `NewProjectDialog` defines its mutation inline instead of via a dedicated hook, unlike every other mutation in this feature.
- **`prettier --check` fails across essentially the entire `frontend/src/features/content-studio/` directory** (discovered this sprint) — including many files untouched by any Image Studio work, so this predates Sprint 4.3 and isn't caused by it. Not a repo-wide issue (the failing files are all under `content-studio/`); likely a formatting-convention drift specific to this feature. This sprint's own new files were formatted individually rather than running `prettier --write` repo-wide, to avoid an unrelated mass-reformat diff — the underlying drift is still unresolved.
- Content generation is slow on current hardware (~3 tokens/sec on `qwen2.5-coder:7b`, CPU-only, 11GB RAM VPS) — a full generation can take up to several minutes even with a warm model. Async/background generation is flagged as a likely future need but out of scope until its own sprint (see ADR-0005).
- `CONTRIBUTING.md` and `DEVELOPMENT.md` are incomplete (both cut off mid-instruction) — flagged during ACF planning, not yet fixed.
- A pre-existing `tsx watch` process (unrelated to this project's work, PID 207157 as of Sprint 3 Phase 1) was noticed during port investigation — not bound to any active port and not interfered with, but worth the user's attention if it's stale.
