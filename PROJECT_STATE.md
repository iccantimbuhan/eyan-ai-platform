## Current Sprint

**Restaurant Operations Platform — Sprint 2D (Sales Reporting & Analytics Foundation) — COMPLETE.** Turns Sprint 2C's raw daily sales records into management reporting — **zero schema changes**, everything computed fresh on read by extending the existing `SalesAggregationService` and `daily-sales-record.mapper.ts`. Five additions: (1) data coverage (`daysInRange`/`daysRecorded`/`missingDays`/`missingDates[]`/`averageSalesPerRecordedDay` — a missing day is never treated as €0), (2) breakdown percentages (each channel/payment-method/category's share of that breakdown's own total, never of `totalSales`, which isn't guaranteed to reconcile), (3) channel performance (`activeDays`/`averageAmountPerActiveDay`, labeled with neutral "Highest recorded sales"/"Highest average sales/day" wording, never "best channel"), (4) reconciliation (`totalSales` vs. `posReportedTotal` vs. `channelEntriesTotal` variances, surfaced never auto-corrected, on both the weekly summary and — new this sprint — the single-day response), and (5) an explicit two-period comparison endpoint (`GET /branches/:branchId/sales/comparison`, both periods supplied by the caller, `changePercent` is `null` — never `Infinity`/`NaN` — when the previous period is zero). A `SalesTrendChart` (recharts, already a project dependency) plots only recorded days, never zero-filling a gap.

Verified: 1125/1125 backend tests pass (18 new), 446/446 frontend tests pass (15 new), both typecheck clean, frontend build succeeds. Live smoke test against the dev database (real HTTP/JWTs, six temporary `DailySalesRecord`s across a 7-day range with one intentional gap, one prior-period record) confirmed coverage/reconciliation/percentage/comparison math all matched hand-computed figures exactly (including the spec's own worked example: POS €1,226.55 vs. channel entries €858.65 vs. €367.90 variance, preserved exactly, never adjusted), missing-day detection correctly listed `2026-07-29`, comparison correctly used only the two explicit caller-supplied ranges, and the new route correctly rejected an unrelated user (403) and an unauthenticated request (401). All temporary data removed afterward; Sprint 1.4's real data and Inventory confirmed unchanged. Explicitly not built (deferred, same non-goals as Sprint 2C): POS/delivery-platform API integration, WhatsApp/OCR/AI ingestion, recipe-based inventory deduction, purchasing, daily closing.

**Also complete — Restaurant Operations Platform Sprint 2C (Sales Foundation).** Branch-scoped daily sales records, POS report metadata, sales channel/payment-method/category/item breakdowns, and daily/weekly aggregation — the structured replacement for the manager's weekly spreadsheet, built without any POS integration. New Prisma models `DailySalesRecord` (`@@unique([branchId, businessDate])`, one register-closing per branch per day), `SalesChannel`/`SalesPaymentMethod`/`SalesCategory` (Restaurant-scoped configurable master lists, same posture as `Unit`), and four line-entry child tables (`SalesChannelEntry`/`SalesPaymentMethodEntry`/`SalesCategoryEntry`/`SalesItemEntry`). See ADR-0039.

Channel and payment method are kept as two structurally separate concepts (never conflated, never reconciled against each other or against `totalSales`/`posReportedTotal` — every figure is preserved exactly as entered). `SalesCategory` is independent of `MenuCategory` (a POS category printout is not assumed to mean the same thing). Itemized sales snapshot `itemName`/`categoryName` at write time; `menuItemId` is an optional `onDelete: SetNull` cross-reference only, so a later Menu edit can never corrupt historical sales records.

A new `requireSalesRecordAccess` guard reuses the existing `createBranchScopedAccessGuard` factory from Sprint 2A (Inventory) verbatim — no new authorization pattern. Reads are open to any branch role; writes (daily sales records, their four line-entry types, and the three master-list creates) require `requireTenantRole('OWNER', 'MANAGER', 'SUPERVISOR', 'ACCOUNTANT')` — confirmed with the user before implementation.

Frontend: a new Sales page (Branch select + date picker, summary stat cards, a tabbed Channel/Payment Method/Category/Item breakdown, an Add/Edit Daily Sales dialog whose four line-entry sections mirror `RecipeIngredientsDialog`'s add-line pattern) and a new Weekly Sales page (date-range picker, plain stat tiles and lists — a foundation view, not the final AI dashboard).

Verified: 1107/1107 backend tests pass (49 new), 431/431 frontend tests pass (9 new), both typecheck clean, frontend build succeeds. Live smoke test against the dev database (real HTTP/JWTs, temporary reference rows and a temporary Daily Sales Record with one line of each type, cleaned up afterward) confirmed correct daily/weekly retrieval, duplicate-day rejection, cross-restaurant scope-mismatch rejection, unauthorized rejection, and a real `BranchMember`-only CASHIER account correctly reading but being denied every write action, while a MANAGER succeeded at both header and line-entry writes. Sprint 1.4's real data and Sprint 2A's Inventory tables confirmed untouched. Explicitly not built (deferred): POS API/webhook integration, WhatsApp/OCR/AI ingestion, recipe-based inventory deduction, purchasing, food costing, daily closing.

**Also complete — Production Stabilization (Sprint 5.2) — COMPLETE** (unrelated track). Sprint 5.1 shipped the full CRM AI-qualification pipeline but it had never actually completed successfully in production. Root cause traced entirely from n8n's own execution history: `buyingIntent`/`urgency`/`riskLevel`'s CRM write-back validator only accepted `LOW/MEDIUM/HIGH`, but a real model legitimately answers `"UNKNOWN"` when unsure — every such qualification 400'd and stranded the lead at `VALIDATED`. A second bug found only during live validation: Workflow 4's Slack/Email steps referenced `$json`, overwritten by `Assign Salesperson`'s own HTTP response on the real path — fixed by referencing `$('Verify & Parse').item.json` explicitly. `app.set("trust proxy", 1)` was also fixed (unrelated `ERR_ERL_UNEXPECTED_X_FORWARDED_FOR`). Verified live four times. Full report: `tasks/completed/sprint-5-2-production-stabilization.md`.
