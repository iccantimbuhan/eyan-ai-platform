## Open Risks / Known Issues

- ~~Sprint 6.1's migration has never been applied to or exercised against a real database~~ — resolved 2026-07-27: verified against the real EYAN Studio development database (`prisma migrate deploy` applied it with no modification needed; `prisma migrate diff` confirmed zero drift). - **Production nginx doesn't yet proxy `/uploads/` to the backend** — Express now correctly serves generated images (fixed this sprint), but nginx's `eyan.fyi` site config only proxies `/api/`, so a generated image's URL would still 404 in production until a one-line `location /uploads/ { proxy_pass ...; }` block is added manually (sudo-gated, outside version control — see `docs/COMFYUI_SETUP.md#5-production-serving-generated-images` for the exact snippet). Local dev is unaffected.
- **Sprint 4.1 through Sprint 6.6's application code is still not deployed to production** — Sprint 6.1's through 6.6's migrations and full functionality are now all verified against the real development database (see above), but `deploy.sh` still hasn't run since Sprint 3.5, and prior sprints' migrations (including Sprint 5's `AssetReview`/`AssetVersion`/`SavedPrompt.projectId`/`generationTimeMs` additions) are live in production while this development-validated code is not — recommend deploying (and adding the nginx block above) before any further work begins, so nothing builds on an untested deploy of eight sprints' worth of undeployed code.
- **Review assignments are informational only — no real multi-user project access exists** (Sprint 6.3) — assigning a reviewer records intent (queue organization, timeline history) but the assignee gains no ability to view or act on the project; `ContentProject` remains single-owner (ADR-0007). Live-validated as working-as-designed, not a bug. Real project collaboration is a named follow-up for a future, dedicated multi-user/RBAC-expansion sprint.
- **Publishing scheduling has no automatic execution — confirmed scope decision, not a gap** (Sprint 6.4) — a `SCHEDULED` `PublishingRecord` sits indefinitely until a user (or a future admin action) explicitly triggers it; no queue/cron/worker infrastructure exists anywhere in this codebase. `AssetService.publish()` is deliberately the single, stable core a future background executor could call unchanged, but building that executor is a named follow-up for a future sprint, not this one.
- **Only a fake publishing provider is registered** (Sprint 6.4) — `PlatformProviderFactory` mirrors `ImageProviderFactory`'s pluggable registry shape, but no real platform (Facebook, Instagram, LinkedIn, TikTok, YouTube, WordPress) is integrated yet; every "publish" today is a deterministic, no-network-call simulation. Adding a real platform is one new class + one `register()` call, no changes to `AssetService` or its routes — a named follow-up.
- **Publishing performance analytics is computed per-asset, not per-platform** (Sprint 6.5) — `AssetReviewEvent` doesn't carry `platform` as a first-class column (only inside `metadata`), so an asset published to two platforms in overlapping windows could have its `PUBLISH_STARTED`/`PUBLISHED` timing pairs computed across both indiscriminately. Accepted as a "Foundation"-level approximation, named as a follow-up.
- **The `"analytics"`/`"dashboard"` seeded RBAC permissions remain unused** (Sprint 6.5/6.6) — the new analytics/dashboard endpoints and pages stay `authenticate`-only, consistent with every other Content Studio route (see ADR-0011); these permissions are available for a future cross-user, admin-facing analytics view, not needed for the current per-owner rollups.
- **The Production Dashboard's platform-wide views loop/merge across every project a user owns in the service layer** (Sprint 6.6, same posture `AssetService.list()` and `AnalyticsService.getPlatformSummary()` already established in 6.5) — fine at demo/portfolio scale (a handful of projects per user), not a database-level rollup.
- **Asset Library aggregation is in-memory, not a database-level query** — `AssetService.list()` fetches up to 500 rows per source and merges/filters/paginates in application code, a documented, deliberate scale boundary (see `docs/ASSET_LIBRARY.md`). Fine at portfolio/demo data volumes; would need a database-level `UNION ALL` (or materialized view) before it could handle a real production catalog.
- **Version Compare is side-by-side, not a line-level diff; Version Restore is present but disabled** (future-ready per the Sprint 5 brief, not wired). **QA Score is a plain manually-entered number**, not computed from the checklist.
- **Video Studio's `SUBTITLES`/`CAPTIONS` have no real timestamp/timing sync** (Sprint 6.2), and **video-timestamp annotations (Sprint 6.3) are manually-entered logical markers, not synced to playback** for the same reason — no actual video file exists yet to sync against; both are named, explicit scope simplifications, not silent gaps.
- **Duplicating an image re-generates it rather than copying the file** — there's no file-copy primitive on `StorageProvider`, and two `GeneratedImage` rows pointing at one stored file would make deleting either one corrupt the other. This means an image "Duplicate" isn't byte-identical to the original if the provider is non-deterministic; documented, not treated as a bug.
- **No real ComfyUI instance has ever been exercised**; no ComfyUI instance has been stood up anywhere. `IMAGE_PROVIDER` is still `fake` in production. Gemini and Hugging Face, previously untested against real endpoints, were both exercised for real during Sprint 6.1 validation (2026-07-27): Gemini authenticated successfully but returned a `429 RESOURCE_EXHAUSTED` (free-tier quota exhausted, an account/billing state, not a code defect — the request reached the provider correctly); Hugging Face completed a full real, successful, billable-tier generation end-to-end (`black-forest-labs/FLUX.1-schnell`, image persisted to disk, `COMPLETED` status). - **Known metadata gap, exposed by Gemini, not fixed**: `ImageService.generate()` persists the requested `format` before generation and never reconciles it against what a provider actually returned. `GeminiImageProvider` always produces PNG regardless of what was requested, so a `jpg`/`webp` request against Gemini will store a DB row whose `format` doesn't match the actual file on disk. `ComfyUIProvider` and `HuggingFaceProvider` both derive format from the actual output (filename extension / Content-Type header respectively), so neither is affected the same way, but the underlying gap in `ImageService` is unchanged.
